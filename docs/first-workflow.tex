\maketitle

\begin{abstract}
You will build a small application that watches a mailbox, asks a language
model to draft a reply to each message, and asks \emph{you} to approve it
before anything is sent. It runs continuously as a service, and by the end of
the tutorial it is running on a server. It is short enough to read in one go,
but it already contains everything that makes ZipperGen worth
using: two participants, a model call, an explicit human decision, a branch
owned by the decider, and a loop that keeps the whole thing alive.

Development happens in an ordinary directory with ordinary command-line tools.
You can write the workflow yourself or ask a coding agent such as Claude Code
or Codex to help. This tutorial shows both paths and points out where human
input is needed.
\end{abstract}

After sending or discarding the reply, the service waits for the next message
and repeats. The loop keeps it running as a service.

Concretely, you want this to happen:

\begin{notebox}{Incoming message}
Could we move our meeting to Thursday afternoon?

\smallskip
\textbf{Proposed reply}\\
Thursday afternoon works for me. How about 3pm?

\smallskip
\texttt{[ Confirm ] [ Decline ]}
\end{notebox}

Two participants exchange messages, and one local action asks a person. What
happens next depends on that person's answer. ZipperGen makes this coordination
explicit and readable.

\begin{notebox}{What you need}
\begin{itemize}
  \item Python 3.11 or newer and ZipperGen installed.
  \item The first run uses a mock model and terminal approval.
  \item For the Telegram section, a bot token, if you want the approval to
        arrive on your phone.
\end{itemize}
\end{notebox}

\section{What comes out}

The workflow is visible, readable Python:

\begin{lstlisting}[language=Python]
@workflow
def email_approval() -> int:
    Mailbox: message = next_unread_message()
    while message @ Mailbox:
        Mailbox(message) >> Writer(message)
        Writer: draft = draft_reply(message)
        Writer(draft) >> Mailbox(draft)
        Mailbox: approved = approve_reply(draft)
        if approved @ Mailbox:
            Mailbox: handled = send_reply(draft, handled)
        else:
            Mailbox: handled = discard(handled)
        Mailbox: message = next_unread_message()
    return handled @ Mailbox
\end{lstlisting}

Read it top to bottom and you have the entire message order. Five things are
worth noticing.

\texttt{Mailbox(message) >> Writer(message)} is a message. The left side sends,
the right side receives, and the names in brackets say which variables carry
the value.

The line beginning \texttt{Writer:} is an action performed by one participant.
\texttt{draft\_reply} is an \texttt{@llm} action, which is a model call with a
prompt and a declared output.

\texttt{Mailbox: approved = approve\_reply(draft)} is a \texttt{@human} action. It
stops and waits for a person.

\texttt{if approved @ Mailbox} is a decision, and the \texttt{@ Mailbox} says who
makes it. That annotation is the important one, and the next section shows why.

\texttt{while message @ Mailbox} is a loop, owned the same way. The
\texttt{Mailbox} decides each round whether there is another message to handle.
\texttt{next\_unread\_message} waits until there is one, so in practice that
decision is always yes and the workflow keeps running.

\begin{notebox}{Mailbox handling stays local}
Mailbox handling involves waiting for new mail, choosing between polling and
blocking, and marking each message as handled. All of it sits behind
\texttt{next\_unread\_message}, whose contract is one sentence: \emph{return the
next message, waiting if there is none}. Here it takes the oldest
\texttt{.txt} file from \texttt{mailbox/} and renames it \texttt{.done}, making
each message one-shot even across a crash. The same coordination works with a
real inbox.
\end{notebox}

\section{Inspect the projected programs}

The workflow has one decision and \texttt{Mailbox} owns it. Ask the agent for
the \texttt{Writer}'s projected program:

\begin{lstlisting}[style=agent]
> What does the Writer actually run?
\end{lstlisting}

\begin{lstlisting}[style=agent]
  $ zg show --agent Writer

  @role('Writer')
  def email_approval__Writer() -> None:
      while recv_decision('Mailbox'):
          message = recv('Mailbox')
          draft = draft_reply(message)
          send('Mailbox', draft)

The Writer receives the loop decision each round and drafts one reply.
Mailbox owns the later approval decision, so it appears only in Mailbox's
program.
\end{lstlisting}

Run it yourself and you get the same projection. Now compare the
\texttt{Mailbox}, which owns both the loop and the decision:

\begin{lstlisting}[style=shell]
zg show --agent Mailbox
\end{lstlisting}

\begin{lstlisting}[language=Python]
@role('Mailbox')
def email_approval__Mailbox() -> int:
    message = next_unread_message()
    while message:
        send_decision('Writer', True)
        send('Writer', message)
        draft = recv('Writer')
        approved = approve_reply(draft)
        if approved:
            handled = send_reply(draft, handled)
        else:
            handled = discard(handled)
        message = next_unread_message()
    else:
        send_decision('Writer', False)
    return handled
\end{lstlisting}

\begin{notebox}{The Writer has no approval branch}
ZipperGen generated both local programs from the workflow. Put them side by
side: \texttt{Mailbox} has code for each of its two control structures, while
\texttt{Writer} has code for only one of them.

The \texttt{Writer} participates in the loop, so \texttt{Mailbox} sends it the
loop decision every round and sends the final false decision on exit. The
\texttt{send\_decision} in the \texttt{else} carries that final decision.

The approval belongs entirely to \texttt{Mailbox}. The \texttt{Writer}
participates in neither branch, so projection erases that decision from its
program. Its execution proceeds independently of the answer.

Hand-written multi-agent systems often fail here when one agent waits for a
message that another branch omits. Projection derives the required control
recipients from the workflow.
\end{notebox}

These projection rules carry a formal guarantee. For well-formed workflows,
complete executions of the projected local programs produce exactly the
behaviours of the global protocol, up to generated control messages. Every
finite projected execution prefix can also be extended to a complete one. The
second property is the formal deadlock-freedom guarantee.

\section{Run it}

First put something in the mailbox. A message is just a text file:

\begin{lstlisting}[style=shell]
mkdir -p mailbox
echo "Can we meet on Thursday" > mailbox/01.txt
\end{lstlisting}

Put the files directly in \texttt{mailbox/}. A plain one-line file is the
message body, and headers such as \texttt{From} and \texttt{Subject} are
optional.

Validation also makes unexpected setup inputs visible. For this workflow it
must report:

\begin{lstlisting}
OK   workflow inputs: none, the run starts without setup questions
\end{lstlisting}

The mock backend works without a model key and answers model calls with a
placeholder:

\begin{lstlisting}[style=shell]
zg run --llm mock
\end{lstlisting}

\begin{lstlisting}
No real model is in use: every participant answers with the mock. Assign one with 'zg model assign TARGET NAME'.

REQUEST · Mailbox

Proposed reply:

[draft_reply:draft]

Send this reply? [y/n]: y
✓ Mailbox · reply sent
\end{lstlisting}

The process now waits for the next message. Drop another file into
\texttt{mailbox/} from a second terminal and it wakes up and handles that one
too. Answering \texttt{n} takes the other branch.

\texttt{mailbox/01.txt} is now \texttt{mailbox/01.done}. That rename is what
stops a message being answered twice, including after a crash.

Stop it with \texttt{Ctrl-C}. For a run that ends by itself, add two new
messages and give it a budget:

\begin{lstlisting}[style=shell]
echo "Please send the notes by Friday" > mailbox/02.txt
echo "Can we talk next week?" > mailbox/03.txt
printf 'y\nn\n' | zg run --llm mock --option max_messages=2
\end{lstlisting}

\begin{lstlisting}
{"result": 1}
\end{lstlisting}

The two answers approve the first reply and decline the second. The result
counts replies sent, so it is one.

\begin{notebox}{Testing a specific branch}
\texttt{mock} supplies placeholder answers for model actions. A
\texttt{@human} action still reads an answer from the terminal or its assigned
connector. Pipe \texttt{y} or \texttt{n}, as above, when a test needs a fixed
human decision. Use \texttt{--llm scripted:replies.json} when a model answer
must be fixed.
\end{notebox}

\section{Use a real model}

Create a named configuration and assign the Writer to it:

\begin{lstlisting}[style=shell]
zg provider configure openai-main openai
zg provider set-credential openai-main
zg model configure writer openai-main gpt-4o-mini
zg model assign Writer writer
zg model
zg run
\end{lstlisting}

The model identity and assignment are written to \path{zippergen.toml}, so they
travel with the project. The credential command reads the API key through a
hidden prompt and saves it privately for the named provider connection on this
computer.
You can instead export the key before running the command. Several
participants can share the same named configuration, and one exact action can
be assigned with a target such as \texttt{Writer.draft\_reply}.
\texttt{zg run -{}-llm mock} remains useful as a temporary override.

Temperature is portable model behavior. An individual
\texttt{@llm(temperature=...)} declaration overrides the named configuration.
Zero reduces sampling variation but does not guarantee identical answers from
a hosted model. If a selected model removed sampling controls, ZipperGen
reports that incompatibility.

When working by hand, you can also run \texttt{zg model configure} and
\texttt{zg model assign} with no values. ZipperGen then asks the questions and
shows the available choices. It asks for the provider connection and model
separately. Full commands remain better for scripts and coding agents.

\section{Runs that survive interruption}

Add \texttt{--durable} to a foreground run to record each step and resume from
its committed position after an interruption:

\begin{lstlisting}[style=shell]
echo "Could we meet on Tuesday?" > mailbox/04.txt
zg run --durable --llm mock
\end{lstlisting}

\begin{lstlisting}
Workflow email_approval: valid
No real model is in use: every participant answers with the mock. Assign one with 'zg model assign TARGET NAME'.
Run email_approval-20260831-132719-612865000

REQUEST · Mailbox

Proposed reply:
...
\end{lstlisting}

Press Ctrl-C while it waits for your approval, then:

\begin{lstlisting}[style=shell]
zg run inspect --agent Writer
zg run --resume
\end{lstlisting}

The model result and control position committed before the interruption are
preserved, so this run resumes at the approval and skips another draft. A crash
during an external call can still repeat that call if its result had not yet
committed.

To abandon the selected run, stop it with Ctrl-C and use \texttt{zg run
reset}. This permanently discards its record and SQLite state and clears the
current run. Add \texttt{-{}-archive} when you want a recoverable private copy.
Start another run with \texttt{zg run -{}-durable}. Starting a new durable run
also discards an older selected development run.

While a durable run is active in one terminal, another terminal can keep its
program position open and refresh it once per second:

\begin{lstlisting}[style=shell]
zg run inspect --watch --agent Writer
\end{lstlisting}

Pressing Ctrl-C in this view closes the view and leaves the run active.

For a long-running workflow, continue a foreground durable run with
\texttt{zg run -{}-resume}. A deployment restarts through its service manager.
In both cases, committed state preserves the workflow position across an
ordinary stop.

\section{Deploy it}

The ordinary deployment command prepares, checks, and starts the service. For
this example it first asks for the mailbox directory. Enter the project
directory you used above, such as \texttt{mailbox}. ZipperGen records its
absolute path so the deployed service continues watching that directory from
outside its immutable source bundle:

\begin{lstlisting}[style=shell]
zg deploy
\end{lstlisting}

Every model, assistant CLI, and connector must pass a readiness probe before the
service starts:

\begin{lstlisting}[style=shell]
zg deploy logs
zg deploy status
zg deploy inspect --watch
zg deploy trace --follow
\end{lstlisting}

\texttt{zg deploy status} distinguishes freshness of the ZipperGen runtime
from freshness of the workflow source bundle. A stale warning means that the
immutable service is still running its previous snapshot. Run \texttt{zg
deploy stop}, then bare \texttt{zg deploy}, to publish and start the update.
Status also names an external action currently in flight, with its elapsed
time, and the last terminal lifeline failure. Trace begins with service and
runtime freshness and identifies a stopped deployment explicitly.
\texttt{inspect -{}-watch} redraws current state. \texttt{trace -{}-follow}
keeps the event table and appends newly committed rows. A live action first
appears as \emph{start}, then \emph{done} or \emph{failed}. Only a static trace
calls a start \emph{incomplete} when no terminal event was recorded. Use status
to decide what is running now.

Use \texttt{zg deploy -{}-no-start} when you deliberately want to prepare and
review a stopped deployment before a later \texttt{zg deploy start}. The usual
command is bare \texttt{zg deploy}.

The trace keeps the newest 10,000 events by default. The budget counts FIFO
rows, not time or bytes. Frequent routine polls can evict an incident, and
events carrying whole emails can make the same count use much more disk.
Measure the real workflow before choosing
\texttt{zg deploy -{}-history-keep N}. Very large budgets also make the
periodic writer-path prune more expensive.

\texttt{zg deploy reset -{}-yes} is different from stopping. It archives and
replaces all durable execution state, including connector progress, and always
leaves the service stopped. A later start begins the workflow again and may
re-read mail already handled.

A deployment you no longer want:

\begin{lstlisting}[style=shell]
zg deploy remove
\end{lstlisting}

Its profile, durable store and log are moved to ZipperGen's trash directory
for recovery. Deploying again builds a new deployment with an empty store.
Removal also deletes its credentials, which must be entered again. A future
deployment rebuilds the managed environment, service files, and bundled
source. \texttt{--purge} also deletes the archived profile, store, and log.

\section{Put it on a server}

Everything above works on your laptop. Continue when you want the workflow to
keep running after you close it.

ZipperGen deploys to a machine you control. Copy the project there, install
ZipperGen, and run the same commands you used locally.

Only the project files cross to the server. The coding agent stays on your
laptop after writing the workflow. The server runs ZipperGen with those project
files and its own credentials.

On an ordinary Linux machine:

\begin{lstlisting}[style=shell]
git clone https://github.com/me/email-approval.git && cd email-approval
python3 -m venv .venv && source .venv/bin/activate
pip install zippergen

mkdir -p mailbox
zg provider set-credential openai-main
zg provider set-credential approval-bot

zg deploy
\end{lstlisting}

The clone supplies the model and connector routing. The two credential commands
read the OpenAI key and Telegram bot token through hidden prompts and store them
outside the project. When \texttt{zg deploy} asks for the mailbox directory,
enter \texttt{mailbox}.

The last command prepares, checks, and starts the deployment. It probes the
model and connector first, so a mistyped token is reported before the service
begins handling approvals. On Linux it installs a small \texttt{systemd}
user service that restarts the workflow if it fails, and enables that unit for
autostart. A server account also needs its user manager to survive logout and
start at boot. If local policy permits it, enable linger once:

\begin{lstlisting}[style=shell]
loginctl enable-linger "$USER"
zg deploy check
\end{lstlisting}

The check reports both systemd autostart and linger. Before leaving the service
unattended, log out once and reboot once, checking \texttt{zg deploy status}
after each. ZipperGen writes the unit file. \texttt{zg deploy status},
\texttt{zg deploy logs}, and \texttt{zg deploy stop} manage it from here.

The workflow's continuous loop makes it a natural fit for a server. Once
deployed, your laptop can close.

The mailbox here is a directory, which is enough to see the shape. Point
\texttt{next\_unread\_message} at a real inbox and the same coordination remains.
\texttt{examples/inbox\_triage.py} is that workflow, reading Gmail and writing
to a spreadsheet.
