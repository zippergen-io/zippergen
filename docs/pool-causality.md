# CPL over work-pool handoffs

Pool actions keep their existing syntax. When a workflow contains CPL guards,
the runtime automatically attaches causal context to jobs. Context includes a
vector clock, the monitor's formula views, and the selected field values needed
by those guards. It stays internal to the execution store, outside the JSON
payload and claim record the application can edit.

## Event semantics

All four pool operations remain single local **act** events. There is no pool
lifeline, synthetic FIFO message, or extra local receive event.

| Operation | Causal effect |
|---|---|
| `put(payload)` | Store the producer's context **after** the action, including its returned job ID. |
| Successful `try_claim()` | Merge the claimed job's published context, then observe the claim action with its result bound locally. |
| Empty `try_claim()` | Observe a local action returning `None`; import nothing. |
| `release(claim)` | Publish the releasing worker's context after release; a subsequent claim imports it. |
| `ack(claim)` | Observe local completion; publish no new handoff. |
| Lease expiry | Retain the last published context. The timer imports no worker state and is not a lifeline event. |

The monitored causal order is generated by local event order, explicit message
edges, and an edge from a job's last put/release event to each successful claim
that reads that publication. Transitive dependencies follow naturally:

```text
Reviewer --message--> Producer --put--> job --claim--> Worker --message--> Reporter
```

SQL locking and FIFO ticket order do not themselves become CPL edges. Claiming
one job does not reveal other jobs or the private state of other workers.
Explicit release exports the context accumulated by that worker; automatic
expiry does not certify that the worker completed or published anything.

The monitor uses the same componentwise clock comparison and latest-view
merge as for messages. Receiving an older job context cannot rewind a newer
causal view. Local previous/since operators still count each pool action once.
Context-aware atoms see `kind == "act"` and an incoming `causal_vc` on successful
claims; `message_vc` and `message_view` remain reserved for message receives.
Recorded claim events expose that incoming clock as `causal_vc` too.

## What a guard establishes

The [approval example](../examples/work_pool_cpl/workflow.py) checks:

```python
approved_for_job = (
    (At[Producer].approved == True)
    & (At[Producer].request == Here.request)
    & (At[Producer].job_id == Here.job_id)
)
```

The job ID is available in the published context because publication occurs
after the put result is bound. A worker can check the producer's approval of
this job without receiving a separate approval message.

`At[Producer]` means the latest **causally visible** Producer event. It is not
a live database query or an immutable view tied to the current claim. Another
message or job may reveal a later Producer event and supersede it. Use request
and job correlation; an approval somewhere in the past is not automatically an
approval for this request. A later revocation needs explicit coordination if
the worker must observe it before acting.

An empty claim is still only a local availability observation. It establishes
neither termination nor the absence of producers. If the first claim must
follow a submission, keep an explicit coordination message. Otherwise polling
with an empty branch is appropriate.

## Durability and scope

The pool mutation, publication context and operation receipt commit in one
transaction. Each receipt retains the original incoming context, so replay
does not consult the job's newer state. The role computes the action on a
separate monitor instance and records its result, monitor and successor state
together afterward. A crash between these commits repeats the same logical
event without double-counting it. Deleting trace history does not affect this.

The policy has a durable identity, `item-handoff-v1`. Executions saved under
the earlier pool semantics must finish on that runtime or start fresh after
archive/reset. Workflows without pools retain their identity.

This support is limited to managed, execution-local pools. It does not make
arbitrary database or connector effects causally transparent, or change lease,
fairness and external-processing idempotency rules.

The implementation extends the runtime's monitored causal relation. It adds
no choreography grammar construct and does not constitute a new preservation
theorem for shared pools. Existing channel/projection results alone are not a
proof of this extension. Tests cover message/pool transitivity, event counts,
job isolation, expiry, release, stale context, and fresh-process recovery.
