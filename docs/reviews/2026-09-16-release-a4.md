# Alpha 4 release checks

Date: 2026-09-16

Candidate: `0.1.0a4`, based on commit `418d30e`, with the version and release
notes updated, source-archive documentation included, a stronger Linux test
and a minimum cryptography version for the Google extra. This record describes
local release preparation, not a published release.

## CI and regression tests

[CI for the security commit](https://github.com/zippergen-io/zippergen/actions/runs/35074983073)
passed on Python 3.11, 3.12 and 3.13, including the type and package jobs.
Those results precede the release-preparation changes described above.

The final local suite on Python 3.12 passed: **1,493 passed, 2 skipped**.
The skips are the Linux-only systemd test and the stale build-tree check
because there is no local `build/lib` directory. Pyright reported no errors or
warnings. `git diff --check` passed.

## Real Linux lifecycle

The opt-in test runs under the unprivileged demo staging account with a
separate temporary project, private home, virtual environment and state.
It does not use the production application's account or credentials.
The installed candidate wheel supplies the runtime.

The test validates and inspects its temporary workflow, deploys and stops it,
marks its test store as an older schema, checks that redeployment refuses it,
resets it, redeploys without starting, starts it and waits for the workflow's
`done` result to be persisted. Finally it stops and removes the test deployment.
This now checks actual execution after restart as well as command outcomes.

Final result: **1 passed in 54.68 seconds**, using Python 3.12.3 and the wheel
whose checksum is recorded below. No test user services or unit files remained
afterward. The production demo remained active with the same main process ID
before and after the tests. Its configuration and installed application were
not changed. The test log was copied back to the local release directory.

This checks a deliberately incompatible schema marker, not every possible
historical store format. It does not test logout or host reboot.

## Dependency audit

The core has no third-party runtime dependencies. Python, the operating
system and external coding CLIs are outside the Python package audit.

The Google extra was resolved for Python 3.11, pinned with distribution hashes
and checked with `pip-audit`. **No known vulnerabilities were found in the
14 resolved packages.** The fresh Python 3.12 Google smoke environment uses
exactly those versions, checked against the audit JSON:

A separate audit of the existing development environment found
`cryptography 49.0.0` affected by
[GHSA-g6cj-pr64-35w5](https://github.com/pyca/cryptography/security/advisories/GHSA-g6cj-pr64-35w5).
The scanner returned two identical entries for the same advisory. This is one
unique finding. It concerns PKCS#7 decryption, and no use of the affected APIs
was found in ZipperGen's source or tests. That source check is not a proof of
unreachability through arbitrary user code.

The Google extra now requires `cryptography>=50.0.0`, the fixed release, so an
upgrade cannot retain version 49.0.0. The local development environment was
updated to 50.0.1. Its follow-up audit found **no known vulnerabilities in 19
installed packages**. The editable ZipperGen distribution was skipped by the
advisory lookup and was covered separately by source review and tests.

These are point-in-time checks of resolved versions. They do not certify all
versions allowed by the dependency ranges or replace future vulnerability
monitoring. The core remains dependency-free.

## Package validation

- Source distribution and wheel built successfully. `twine check --strict`
  passed for both.
- All 69 Python modules in the wheel match the source byte-for-byte. Packaged
  skill resources also match.
- The source archive includes the current changelog, security notes, package
  metadata and strengthened systemd lifecycle test.
- A clean core-only installation reports version `0.1.0a4`, runs CLI help,
  deployment help and the packaged skill, and validates/renders the email and
  pool examples. Calendar and CPL pool examples also validate.
- The core-only installation imports Google connector modules without the
  optional libraries and gives the expected missing-extra error when those
  libraries are requested.
- The installed wheel executes the pool example and resumes its stored result.
- A separate clean installation with the Google extra passes `uv pip check`.
  Real credential, authorized-session and OAuth-flow constructors work using
  synthetic credentials without network calls.
- **73 Google connector and authorization tests passed against the installed
  wheel and fresh Google libraries.** The test runner came from the existing
  development environment. Assertions verified the package and Google import
  paths before running the tests.

No live Google authorization, calendar write, email or Telegram message was
performed. The assistant filesystem boundary and other release limits are
explained in [the security notes](../security.md) and the changelog.
