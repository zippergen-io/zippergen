# Focused security review before the next alpha

Date: 2026-09-15

This review follows the [operational review](2026-09-15-prerelease.md) at
commit `75d2183`. It examines approval authorization, credential handling,
assistant subprocess boundaries, deployment paths and Google authorization
handoffs. It combines source inspection with synthetic adversarial inputs.
It is not an independent penetration test or a complete security audit.

## Confirmed problems and fixes

### Execution lock could modify a substituted file

Both lock inspection and acquisition opened the lock path while following
symbolic links, then changed its permissions. Acquisition also truncated it.
A hard link had the same problem. Special files were not rejected before
modification either.

The shared opener now uses `O_NOFOLLOW`, inspects the open descriptor and
requires a regular file with one link before changing permissions. A
nonblocking open prevents waiting on a special file before inspection.
Six regression cases cover symbolic links, hard links and FIFOs through both
entry points. They verify that the target's contents and permissions survive.
All six failed before the fix.

This is a local file-substitution problem. Exploiting it requires the ability
to place a file at the lock path. It is not evidence of remote access or
privilege escalation. The operator must still control the parent directories.

### Google handoff validation was too permissive

A correctly checksummed handoff could contain missing refresh credentials,
inconsistent client IDs or malformed scope metadata. The accept command could
then replace the saved credential with unusable data. A non-ASCII checksum
also escaped the expected error handling, and the Base64 decoder ignored
invalid characters.

The decoder now checks the encoded alphabet and checksum format, requires
nonempty string scopes and refreshable credential fields, and checks that the
inner and outer client IDs agree. Errors do not quote credential values.
Eight regression cases reproduced the earlier failures. Three CLI cases also
verify that invalid input leaves existing credentials and provider metadata
unchanged.

The handoff checksum is not authentication. These checks do not prove that
Google issued the token or granted the claimed scopes. The handoff must come
from a trusted authorization session, and Google enforces the actual grant.
The new [security notes](../security.md) make this distinction explicit.

Valid handoffs produced from Google's desktop credentials retain the required
fields. Test doubles that omitted `client_secret` now include it. The existing
checksum-corruption test was also corrected to always change the final digit.

### Assistant locale wildcard bypassed the environment allowlist

The environment filter accepted every name beginning with `LC_`. A custom
credential under a name such as `LC_WORKFLOW_TOKEN` therefore reached either
assistant backend. Two regression cases reproduced that behavior.

The filter now lists standard locale variables explicitly. Tests check both
that custom secret names are removed and that normal locale settings survive.
Existing tests continue to cover model keys, connector credentials, CLI login
locations and the subprocess argument list.

## Boundaries checked

| Boundary | Evidence and scope |
| --- | --- |
| Telegram actor and chat | Existing callback, command and reply tests reject unauthorized actors. New tests check a wrong chat and a missing actor with a token owned by the deployment. |
| Approval replay | A new test completes an old task, reuses its name in a fresh store and confirms that the old token cannot complete the new task. Repeating the new answer cannot change its result. This tests the store/token boundary, alongside the existing CLI reset tests. |
| Shared Telegram bot | Existing tests preserve responses addressed to another deployment, including when approver policies differ. |
| Credential diagnostics | Google and Telegram privacy tests exercise transport, HTTP and decoding failures using synthetic secrets, including formatted exception chains. |
| Private files | Existing tests cover owner-only writes and rejection of secret-file symlinks. New execution-lock tests cover substituted lock files. |
| Deployment paths | Existing tests cover escaping source symlinks, systemd path quoting and refusal to reset or delete external files referenced by a profile. |
| Assistant inputs | Existing adapter tests keep prompts out of command arguments and filter workflow credential variables. The implementation passes prompts through stdin and does not construct a shell command from workflow input. |
| Google grants | Existing tests check scope coverage and rejection of serialized credentials missing required scopes. New tests cover handoff validation before saving. Actual grant enforcement remains Google's responsibility. |

## Important remaining limit

The assistant environment filter is not filesystem isolation. The adapters
select a working directory and CLI permission options but do not create a
separate operating-system identity or a filesystem read allowlist for the
workflow's credentials.

A local probe used only a temporary synthetic secret, with mode `0600`,
outside a temporary working directory. A Python subprocess given either
backend's filtered environment could still read it. This demonstrates the
limit of environment filtering alone. It does not test or bypass the actual
Codex or Claude sandbox.

The README and security notes now distinguish the two boundaries. Protecting
credentials from an assistant processing hostile content requires additional
isolation. Putting the entire workflow under a dedicated account is not
sufficient to separate that workflow's assistant from its connector secrets.
ZipperGen does not currently provide that separation automatically.

## Scope limits and compatibility

- No live coding model, Google authorization, Telegram message or production
  service was used. Test credentials and approval messages were synthetic.
- Workflow Python, deployment commands, OAuth client files and dependencies
  are operator-trusted inputs. This review does not make them safe to accept
  from arbitrary third parties.
- This review does not establish resistance to an attacker controlling the
  same account, administrators, parent directories or the host.
- Dependency vulnerability scanning, the hosted demo's HTTP surface and
  real CLI sandbox enforcement were not assessed in this pass.
- Linux systemd execution and the other supported Python versions remain
  release checks. The tests here run on macOS with Python 3.12.
- There is no workflow syntax, SQLite schema or deployment command change.
  Existing executions do not require a reset. Malformed handoffs and unusual
  linked lock files that were previously accepted are now refused.
