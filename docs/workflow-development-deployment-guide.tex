\begin{abstract}
This manual is the comprehensive reference for developing and operating
ZipperGen applications. It explains the Studio lifecycle, global workflows and
local projections, specifications and coding-assistant handoffs, model
configuration, semantic inspection, durable execution, human approval,
deployment, supervision, recovery, troubleshooting, and the corresponding
scriptable commands. It is written for readers who can use a terminal and
editor but do not need to be experienced Python or operations engineers.
\end{abstract}

\begin{notebox}{Looking for the shortest path?}
The companion \path{docs/first-workflow.tex} is the self-contained first-hour
tutorial. It goes directly from a new directory to a specified, inspected,
mock-run, resumed, and prepared deployment. Start there when building a first
workflow; return to this manual when a step needs more explanation or when
configuring real models and production operations.
\end{notebox}

\begin{notebox}{The main promise}
The workflow is always ordinary Python code. A coding assistant may create or
change that code from one visible, versionable workflow specification, but ZipperGen
performs the deterministic work: loading it, validating every projection,
showing what each participant does, comparing semantics, storing durable
execution state, and managing deployment. LLMs propose workflows; ZipperGen
makes them explicit, verifiable, and deliberately deployable. It never treats
opaque model output as an automatically deployed workflow.
\end{notebox}

\section{The mental model}

\subsection{A workflow is a global protocol}

Most agent frameworks distribute control logic among agents. ZipperGen instead
starts with one global protocol: who owns a value, who sends it, who receives
it, who performs an action, and who owns each decision. From that global code,
ZipperGen projects an exact local program for every participant.

\begin{figure}[htbp]
\centering

\end{tikzpicture}
\caption{The prompt-to-production path. The Python workflow remains the

\label{fig:lifecycle}
\end{figure}

For a well-formed protocol, every projected send has a corresponding receive.
The code therefore serves simultaneously as executable behavior, design
documentation, and an audit surface.

A global protocol does not have to be one monolithic function. Reusable or
conceptually coherent subsequences can be given meaningful names so that the
top-level protocol stays a reasonable size. Decorate such a helper with
\texttt{@fragment}, then call it inside a \texttt{@workflow} body:

\begin{lstlisting}[style=python]
from zippergen import fragment, workflow

@fragment
def request_review(draft):
    Writer(draft) >> Reviewer(draft)
    Reviewer: approved = review(draft)
    Reviewer(approved) >> Writer(approved)

@workflow
def reviewed_answer(request: str @ Requester):
    Requester(request) >> Writer(request)
    Writer: draft = write_draft(request)
    request_review(draft)
\end{lstlisting}

A fragment is an authoring-time, reusable piece of the same global protocol.
Its statements are inlined into the surrounding workflow before validation and
projection; it is not a separately deployed workflow, participant, process, or
durable run. It can still be useful when called only once if it names a coherent
protocol stage. Use another top-level \texttt{@workflow} only when the unit
should be loaded, run, and deployed independently.

\subsection{Important words}

\begin{longtable}{p{0.20\linewidth}p{0.73\linewidth}}
\toprule
\textbf{Term} & \textbf{Meaning} \\
\midrule
\endhead
Lifeline & One sequential participant or responsibility boundary. It may
represent an agent, a person, a mailbox, or an external-system role. \\
Message & An explicit transfer of one or more values from one lifeline to
another, written with \texttt{Sender(value) >> Receiver(value)}. \\
Action & Work performed locally at one lifeline: deterministic computation,
LLM work, an external effect, human input, or runtime planning. \\
Owned decision & An \texttt{if} or \texttt{while} guard followed by
\texttt{@ Lifeline}. That lifeline must know the guard value and owns the
choice. \\
Projection & The local program generated for one lifeline from the global
protocol. \\
Workflow spec & A CLI reference such as
\path{zippergen/examples/tutorial_review.py:tutorial_review}: file path, colon, workflow
object name. It selects an existing workflow object; it does not name a
deployment. \\
Store & A SQLite file holding messages, actions, traces, human tasks, and
workflow results. It enables durable resume and replay. \\
Human task & A durable pending request created by a \texttt{@human} action. It
contains the question or rendered content, its pending/completed state, and the
eventual human decision. \\
Task ID & The stable internal identifier of a human task. A trusted local
operator may use it with \texttt{approve --task}. It identifies the task but is
not intended to be an approval credential in an untrusted external link. \\
Task token & A durable random bearer value that maps back to one human task.
External adapters can use it with \texttt{approve --token}; treat it like a
secret approval link. A token does not create another task. \\
Token channel & An arbitrary label such as \texttt{email}, \texttt{telegram},
or \texttt{cli}. It allows the same task to have a separate token for each
adapter; it is not a workflow message channel. \\
Deployment profile & Persistent non-secret settings for a named deployment. \\
Bundle & A timestamped copy of the workflow and its declared support files.
Deployments run from this snapshot, not from a file that may change halfway
through execution. \\
Managed environment & A deployment-specific Python virtual environment with
ZipperGen and declared packages installed. \\
Service manager & macOS \texttt{launchd} or Linux user \texttt{systemd}, used
to start, restart, and supervise a deployment. \\
\bottomrule
\end{longtable}

\subsection{Action kinds}

\begin{tabularx}{\linewidth}{p{0.14\linewidth}X X}
\toprule
\textbf{Decorator} & \textbf{Use it for} & \textbf{Important property} \\
\midrule
\texttt{@pure} & Deterministic local computation & No external I/O or durable
side effect. \\
\texttt{@effect} & Email, files, APIs, databases, or other external mutation &
Make it retry-safe or idempotent. \\
\texttt{@assistant} & Repository-aware work performed by Codex, Claude Code,
or a custom assistant backend & The action, Markdown instruction fingerprint,
typed inputs, owner, and result remain inspectable and durable. \\
\texttt{@llm} & Model generation or judgment & Declare prompts, parse format,
and typed outputs. \\
\texttt{@human} & Confirmation, edit, selection, acknowledgement, or input &
Creates a durable task in SQLite execution. \\
\texttt{@planner} & A model-generated allowed sub-workflow at runtime & Uses a
fail-closed statement grammar. Generated imports, Python bodies, and
\texttt{@pure} helpers are rejected before import. \\
\bottomrule
\end{tabularx}

A planner may generate schema-checked \texttt{@llm} actions when its
\texttt{allow} declaration includes \texttt{llm}. Deterministic
\texttt{@pure} helpers must be defined in reviewed source and passed through
the planner's \texttt{actions} argument. A planner is not the normal mechanism
for coding-assistant source generation.

\section{Project setup and Studio orientation}
\label{sec:studio}

ZipperGen Studio is the recommended way to experience the development cycle.
It is a lightweight, project-aware command environment inside the ordinary
terminal. It does not replace the operating-system shell, Git, the editor, or
the visible Python workflow. Instead, it remembers the project context and
turns the most common operations into short, discoverable commands.

These chapters describe Studio by topic, including optional configuration and
migration details. The shorter companion tutorial deliberately omits those
branches. Here, the project root contains
the canonical specification, generated workflows, tests, and its own Git history; the nested
\path{zippergen} directory contains the framework checkout. Readers who already
have both may skip only that first subsection. Section~\ref{sec:install} later
explains prerequisites and alternatives in more detail.

\begin{notebox}{What is required, and what is optional}
The free local path requires macOS or Linux, a terminal, an Internet connection
for the initial clone and installation, and enough familiarity to copy commands
and edit a file. The built-in mock LLM needs no API key and makes no paid model
calls. Codex or another repository-aware coding assistant is needed only to
generate or refine source from a prompt; the shipped example is the fallback.
OpenAI and Anthropic accounts, real API keys, and supervised service startup are
all optional exercises, clearly labelled below.
\end{notebox}

\begin{notebox}{What Studio removes from the normal development path}
For the guided local cycle, you do not need to export \texttt{ZIPPERGEN\_HOME},
invent a SQLite filename, copy a task ID, keep two terminals synchronized, or
remember the inspection flags. Studio creates unique durable stores, presents
human tasks inline, records the workflow in the versioned project manifest,
and remembers the current run, view, and named deployment.
\end{notebox}

\subsection{Create the project and framework checkouts}

Open an ordinary terminal. Create the example project, initialize its Git
history, clone the framework below it, and install the framework's command as
an editable user tool:

\begin{lstlisting}[style=shell]
mkdir -p "$HOME/Projects"
cd "$HOME/Projects"
mkdir zippergen-tutorial
cd "$HOME/Projects/zippergen-tutorial"
git init
git clone https://github.com/zippergen-io/zippergen.git zippergen
uv python install 3.12
uv sync --project zippergen --python 3.12
uv tool install --force --editable ./zippergen
zippergen --help
\end{lstlisting}

The parent is now the tutorial project and coding-assistant root. Its nested
\path{zippergen} directory is a separate framework checkout containing
\path{AGENTS.md}, the workflow skill, framework source, and shipped examples.
Studio will create the application project's fixed \path{specification.md}
when you enter \texttt{workflow edit-spec}; there is no prompt directory or
prompt filename to choose. A later described change uses the ignored scratch
file \path{.zippergen/refinement.md}. Only \texttt{workflow refine-spec} reads
it, and a successful revision consumes it.
\texttt{uv sync} creates the framework's local environment;
\texttt{uv tool install --force --editable} makes the short \texttt{zippergen} command
available while still using this editable checkout. The project, checkout,
downloaded Python, and environment survive closing the terminal or rebooting.
The final help output should list \texttt{studio} among the available
top-level commands. You do not run \texttt{model} here: \texttt{model} is a
short command entered later inside Studio.

\begin{notebox}{If your existing tutorial checkout is flat}
An older version of this manual cloned ZipperGen directly into
\path{zippergen-tutorial}. In that layout the project root itself contains
\path{AGENTS.md}, \path{pyproject.toml}, and \path{src}, and
there is no nested \path{zippergen} directory. Do not add a
\texttt{zippergen/} prefix to framework paths. The Studio creation command is
still simply \texttt{workflow edit-spec}. For that flat checkout, run these equivalent
installation commands from its root:
\begin{quote}
\texttt{uv sync --python 3.12}\\
\texttt{uv tool install --force --editable .}
\end{quote}
\end{notebox}

If \texttt{git} is not found, install the standard Git package for your
operating system and repeat the first listing. If \texttt{uv} is not found but
\texttt{curl} is available, install it with:

\begin{lstlisting}[style=shell]
curl -LsSf https://astral.sh/uv/install.sh | sh
\end{lstlisting}

Restart the terminal if the installer requests it, then continue from:

\begin{lstlisting}[style=shell]
cd "$HOME/Projects/zippergen-tutorial"
uv python install 3.12
uv sync --project zippergen --python 3.12
uv tool install --force --editable ./zippergen
zippergen --help
\end{lstlisting}

If \path{$HOME/Projects/zippergen-tutorial/zippergen} already contains the
framework checkout, do not clone over it. Enter the project and inspect both
Git repositories separately:

\begin{lstlisting}[style=shell]
cd "$HOME/Projects/zippergen-tutorial"
git status --short
git -C zippergen status --short
\end{lstlisting}

An empty result from each command means that repository has no uncommitted
changes. Before the first Studio \texttt{project init}, the outer command may
show \texttt{?? zippergen/}; project initialization adds the local framework
checkout to the outer \path{.gitignore}. Do not run
\texttt{git pull}, delete files, or reset changes you do not understand merely
to begin the tutorial.

\section{Specification and workflow development}

The following topics explain every box in Figure~\ref{fig:studio-path} using a
reviewed-answer workflow created from a natural-language specification. Studio
and the coding assistant handle its Python filename and symbol. The shipped
\path{zippergen/examples/tutorial_review.py:tutorial_review} is the
deterministic fallback if a coding assistant is not available.

\subsection{Initialize the project in Studio}

Keep the first terminal in the Git root and start Studio:

\begin{lstlisting}[style=shell]
cd "$HOME/Projects/zippergen-tutorial"
zippergen
\end{lstlisting}

Expected beginning:

\begin{lstlisting}[style=shell]
ZipperGen Studio
Session context
Project    zippergen-tutorial
Root       /path/to/zippergen-tutorial
Workflow   WARN not configured
Assistant  OK Codex CLI found
Start      Type a command or describe what you want.
           Press Tab to complete. Use 'help' for the short path.
Next
  project init
zippergen [no workflow]>
\end{lstlisting}

Everything after the last line is a Studio command. Do not prefix Studio
commands with \texttt{zippergen}. Enter \texttt{help} now; it shows the small
creation-to-deployment path. Enter \texttt{help all} only when the complete
exact reference is useful. The assistant line may instead be a warning when
neither supported CLI is installed; specification, deterministic inspection,
mock execution, and the rest of Studio remain available.

The command vocabulary has four main areas. Everything that changes or
explains the application design lives below \texttt{workflow}: creation,
refinement, coding-assistant implementation, selection, semantic views,
validation, review, and history. Everything about model connections,
configurations, checks, and assignments lives below \texttt{model}.
Development execution, decisions, traces, and inspection remain below
\texttt{run}. Creating and operating an installed application, including its
durable state and decisions, lives below \texttt{deploy}. Thus a beginner can
type \texttt{workflow}, \texttt{model}, \texttt{run}, \texttt{deploy}, or
\texttt{current} to recover the next step instead of remembering several
unrelated nouns.
The small cross-cutting \texttt{settings} command covers global Studio
preferences rather than application behavior.

The \texttt{studio doctor} command checks the local development front door:
manifest, editor, coding assistant, and natural-language interpreter. It does
not contact OpenAI, Anthropic, Mistral, or a local model endpoint. Codex and
Claude are optional external programs with their own installation and login;
they are deliberately not Python dependencies of ZipperGen.

Two deliberately explicit process commands cover reloading and updating
Studio. Use \texttt{studio restart} to replace the running process and import
source that is already installed. The replacement keeps the current directory
and reloads the project context saved on disk. It does not open a nested
Studio.

When Studio is running from the ZipperGen Git checkout, use:

\begin{lstlisting}[style=shell]
studio update
\end{lstlisting}

This command finds the actual ZipperGen source checkout. It does not assume
that the checkout is named \texttt{zippergen} or that it is directly below the
project directory. It refuses tracked local changes and detached-HEAD state,
runs \texttt{git pull --ff-only}, synchronizes the environment with
\texttt{uv} when dependency metadata changed, and then restarts the same
Studio session. The application project remains the current project. Existing
deployment bundles remain immutable and are not restarted or replaced.

For a packaged installation, Studio explains that the corresponding package
manager must perform the update. Do not confuse either Studio process command
with \texttt{deploy restart [NAME]}, which restarts an installed deployment.

Every newly prepared deployment records the ZipperGen version and, for a
source checkout, the Git revision installed into its managed environment.
\texttt{deploy show NAME} displays that runtime provenance. It reports a log
exception as the current \texttt{Cause} only while the current service is
failing. An error left by an older deployment generation is labelled
\texttt{Previous failure}. Preparing a deployment also establishes a new log
generation boundary without deleting the earlier log history.

Press Tab at any point while entering a command. Studio completes commands and
subcommands and, where relevant, offers the workflows, participants,
LLM-active participants, providers, remembered deployment, and project files
that are valid in the current context. For example, type \texttt{wor} followed
by Tab to obtain \texttt{workflow}; after selecting the tutorial workflow,
\texttt{workflow show agent W} followed by Tab completes \texttt{Writer}. When several
matches exist, the completion menu explains each one. When exactly one match
exists---for example, \texttt{resu} for \texttt{resume}---the bottom line shows
that match and its explanation even though no menu is necessary. Use the up
and down arrows for private per-project command history. A faint suggestion
from that history is accepted with the right arrow. This interactive support
is provided by \texttt{prompt-toolkit}; scripts and piped input keep the plain
non-interactive input path.

Initialize the visible project contract, then inspect the initial dashboard:

\begin{lstlisting}[style=shell]
project init zippergen-tutorial
current
\end{lstlisting}

Studio creates \path{zippergen.toml} and safe Git
ignores for \path{.zippergen}, the nested framework checkout, and the optional
transparent runtime. The manifest, its one \texttt{workflow\_entry}, and the
canonical \path{specification.md} are project source and may be committed. A
clone can therefore identify its workflow without a private workspace record.
Timestamped tasks, semantic baselines, runs, and secrets remain
in private Studio state outside the project. Studio mirrors only the current
generated task at \path{.zippergen/current-task.md}; Git ignores that file.
Repeating \texttt{project init} is safe; it reports the existing manifest
instead of overwriting it.
Use \texttt{project rename "NEW NAME"} to change the logical name later. This
edits only the versioned manifest: the directory, Git checkout, workflows,
deployments, and private workspace identity remain unchanged.

If you later need a reset, do not delete hidden directories or visible project
files by hand. Plain \texttt{project reset} first asks which scope you mean:
\emph{Fresh design cycle}, \emph{Studio state only}, or \emph{Cancel}. The
state-only choice archives runs and stores, assistant-task/refinement/command
history, model/provider preferences, development secrets, generated tasks, and
the scratch refinement while retaining every visible project file. The fresh
choice additionally archives \path{zippergen.toml},
\path{specification.md}, and legacy prompt material. Both keep workflow source,
tests, Git history, the nested framework checkout, and deployments. Archives
are owner-only below \path{ZIPPERGEN_HOME/resets}.
Neither reset scope changes the global preferences shown by
\texttt{settings}.

This distinction explains the complete restart sequence. Choose the fresh
design cycle, confirm it, then enter \texttt{project init} and \texttt{workflow
edit-spec}.
The manifest is genuinely new and the specification contains only the writing
guide described below, not the previous requirements. For automation, the
explicit commands are \texttt{project reset fresh --yes} and
\texttt{project reset state --yes}; ambiguous
\texttt{project reset --yes} is rejected.

\begin{notebox}{How Studio reports outcomes}
A green \(\checkmark\) means an operation or check succeeded. A yellow
warning sign means setup is incomplete or needs attention, but is not
necessarily broken. A red \(\times\) means an operation or validation check
failed. The symbol always carries the meaning, so the output remains clear
without color. Studio adds color only in an interactive terminal; redirected
output and sessions with \texttt{NO\_COLOR} remain color-free. Optional
providers that you are not using are warnings rather than failures.

Every nonempty command also starts a clearly separated output block. For
example:

\begin{lstlisting}[style=shell]
zippergen [reviewed_answer]> current

+----------------------------------------------------------+
| ZipperGen Studio : current                               |
+----------------------------------------------------------+
Current
-------
\end{lstlisting}

The real terminal uses connected curved Unicode corners, a Unicode vertical
bar, and a middle dot; the connected ASCII box above is print-friendly. The
banner repeats only the command family, never its prompt text, paths, model
values, or secrets. It therefore remains short even for a long
\texttt{workflow edit-spec} or \texttt{workflow edit-refinement} command. Blank input and
\texttt{exit} produce no banner. Use \texttt{settings set output compact} only
if a one-line boundary is preferable.

Inside the banner, Studio uses the same hierarchy for every command: a section
title and rule, explicit column headings, another rule separating those
headings from the actual rows, and a standalone \texttt{Next} section when
guidance is useful. Success, warning, or failure appears before the data it
describes. Thus \texttt{project}, \texttt{workflow}, \texttt{model},
\texttt{language}, \texttt{run}, and \texttt{deploy} results do not require
the reader to learn different output layouts.
Long fields and table rows wrap to the terminal width, so a path, assistant-check
command, or assistant explanation no longer extends far beyond its heading.
Wide multi-column data lists may use more terminal width than prose
key/value tables. Identifier and timestamp cells remain one line and shorten
with an ellipsis instead of being split into uncopyable fragments; the
corresponding \texttt{show} or \texttt{path} command exposes the exact value.
The managed \texttt{run} and \texttt{resume} commands use this same renderer;
they do not switch to a second set of bare runtime messages.
\end{notebox}

Studio accepts exact commands as well as ordinary-language requests, and it
discovers a usable terminal editor automatically. Neither feature needs
configuration before the first specification. The language, learning,
settings, and editor controls are collected later in
Section~\ref{sec:studio-preferences}; continue directly to specification
authoring.

\subsection{Write the canonical specification}

Long requirements do not belong in a single-line terminal question, and the
user should not have to invent or remember a prompt filename. Enter
\texttt{workflow edit-spec}. Studio creates the fixed project file
\path{specification.md}, opens it in the automatically discovered editor, and
waits. On the first creation it contains a short comment explaining what a
specification should cover and which development mechanics to omit. Write
below that comment or replace it with the complete text below. Studio removes
the guide automatically after real requirements are saved; leaving the guide
untouched does not create an assistant task. Copying into an editor is reliable
even when a terminal's interactive question cannot accept a multiline paste.

\begin{lstlisting}[style=shell]
workflow edit-spec
\end{lstlisting}

\begin{lstlisting}[numbers=none]
# Reviewed Answer

Produce a helpful answer to a request, subject to automated review and explicit
human approval.

## Participants and behavior

- Requester initially owns `request` and `max_retries`.
- Writer uses an LLM to draft and revise an answer.
- Reviewer uses a separate LLM to assess every draft.
- HumanApprover owns the decision to approve or reject a draft after the
  automated assessment.
- A rejection sends the draft back to Writer while retries remain.
- Never return an unapproved draft. Return an explicit failure after retry
  exhaustion.
- Keep human delivery independent of workflow source. HumanApprover's
  `@human` actions use the terminal by default and may later be assigned a
  reusable Telegram configuration.

## Inputs and operation

- The application accepts a `request` input, defaulting to
  `Explain why the sky is blue in two sentences.`
- It accepts an integer `max_retries` input, defaulting to `2`.
- Use the deterministic mock model by default so the application can be tried
  without a paid model account.
- A deployment may instead use OpenAI or Anthropic. Request the corresponding
  API key only when that provider is selected.
\end{lstlisting}

Save the file and exit the editor. Studio reads the whole UTF-8 document,
preserves its paragraphs and lists, and wraps it in repository-aware
instructions. It prints a compact table instead of repeating the long text:

\begin{lstlisting}[style=shell]
+----------------------------------------------------------+
| ZipperGen Studio : workflow edit-spec                    |
+----------------------------------------------------------+
Specification updated
  File           [success] specification.md
  Implementation           absent
  Next                     workflow implement
\end{lstlisting}

There is no prompt ID, numbered prompt file, or ordering operation. The
canonical document is always \path{specification.md}; it is ordinary project
source and should be reviewed and committed with the Python workflow. The
generated, non-secret handoff is always
\path{.zippergen/current-task.md}; Studio also keeps timestamped private task
history outside Git.

Projects created by an older Studio may still contain an ordered prompt
ledger. On first specification access, Studio combines its active entries into
\path{specification.md} and preserves the old files as migration history. The
former \texttt{workflow prompts} command is deliberately unavailable: all new
work uses one canonical specification and one optional scratch refinement.

The implementation request asks the assistant to identify participants,
ownership, messages, action kinds, decisions, loops, deployment needs, safety
assumptions, and success examples before editing. It also requires tests,
validation, semantic views, and all exact local projections. No workflow file
has been created yet; the implementation subsection starts the coding
assistant on this request.

Notice that the specification does not choose a Python filename or symbol,
request tests and validation, or repeat the prohibition on deployment. Those
are development mechanics supplied automatically by Studio's generated task.
The specification contains only durable application intent. After generation,
Studio discovers the resulting workflow and records its one entry point in
\path{zippergen.toml}. For hand-written source, \texttt{workflow list} discovers
the displayed path and \texttt{workflow import PATH.py:NAME} adopts it. The
entry point therefore travels with the project.

The everyday specification commands are intentionally uniform:

\begin{lstlisting}[style=shell]
workflow show spec    # read the canonical requirements
workflow edit-spec    # reopen the same specification.md
workflow path         # print its absolute path only when another tool needs it
workflow status       # inspect the implementation lifecycle
workflow status --details # add task IDs, refresh links, and record paths
workflow history      # list specification and implementation history
\end{lstlisting}

The ordinary status and \texttt{current} dashboards intentionally hide
generated task filenames, request IDs, and semantic-baseline paths. Those are
auditable plumbing rather than concepts required for daily work.
\texttt{workflow status --details} and \texttt{workflow history} expose them
when diagnosis or traceability requires them.

An empty specification is rejected. Never put an API key or other secret in
it. For a genuinely short experiment, \texttt{workflow edit-spec DESCRIPTION}
writes the same canonical file without opening an editor. Advanced users may import an
existing UTF-8 document with \texttt{workflow edit-spec --file PATH}; Studio copies
its content into \path{specification.md} and does not retain that source
filename as project configuration.

Studio records the specification fingerprint and generated source fingerprint
in the committed \path{zippergen.lock} file after implementation. From the
manifest, specification, source, and lock, it derives \emph{absent},
\emph{stale}, \emph{current}, or \emph{external}. This result is the same on a
fresh clone because it uses no private workspace state.

Projects made with an older Studio may still contain
\path{prompts/index.toml} and numbered prompt files. On the first
\texttt{workflow show spec}, \texttt{workflow edit-spec}, or \texttt{workflow
refine}, Studio safely
combines their active contents into \path{specification.md} and keeps every old
file as history. New work then uses only the canonical specification model.

\begin{notebox}{Why Studio creates a brief instead of hidden code}
Natural language is flexible; executable coordination must be precise. The
brief supplies repository rules and completion checks. The resulting ordinary
Python file is inspected and versioned. ZipperGen never treats opaque model
output as an automatically deployed workflow.
\end{notebox}

\subsection{Implement the specification with a coding assistant}

At the same Studio prompt, enter:

\begin{lstlisting}[style=shell]
workflow implement codex
# Or, when Claude Code is installed:
workflow implement claude
\end{lstlisting}

Choose one of the two commands; do not run both for the same implementation
request. After \texttt{settings set assistant codex} or
\texttt{settings set assistant claude}, bare \texttt{workflow implement} uses
that global preference. Studio runs
the selected local coding assistant once in the project root and tells it to
read \path{.zippergen/current-task.md}. Just before launch, Studio applies
the freshness check described above, so the file contains the current
canonical specification. There is no task path or prompt file to copy. The
assistant autonomously inspects and edits the application project within its
configured permission boundary, runs checks, writes a small structured
assistant-check handoff, exits, and returns control to the same ZipperGen Studio
session. The handoff distinguishes the assistant process returning from the
requested checks actually passing. Use
\texttt{workflow implement codex --interactive} only when a conversation or interactive
approval is genuinely needed.

The generated task also explains the tutorial's two-project layout. The
application lives at the tutorial root, while \path{zippergen/pyproject.toml}
defines the environment for the nested framework checkout. It therefore tells
the assistant to invoke the framework from the application root with
\texttt{uv run --offline --project zippergen zippergen ...} and to run
application tests by the explicit \path{tests} path. A bare
\texttt{uv run pytest} at the tutorial root is deliberately forbidden: it can
collect \path{zippergen/tests} while
using an environment that did not install the framework dependencies. The
framework's own suite is separate and is needed only when framework source was
actually changed. Pytest is a declared development dependency installed by the
initial \texttt{uv sync}; the assistant must not add
\texttt{--with pytest}, install packages, or request PyPI access. If the local
environment has not been synchronized after an update, run
\texttt{uv sync --project zippergen} once in the ordinary terminal and then
rerun the assistant deliberately. Studio checks this prerequisite offline
before starting Codex or Claude, so a missing pytest installation does not
consume an assistant run.

For one-shot Codex runs, Studio uses Codex's structured JSON output mode and
shows the final assistant report rather than its raw execution trace. Known
internal model-cache diagnostics are suppressed; unexpected diagnostics are
condensed into warnings. Studio first prints that Codex is working and then
prints periodic elapsed-time heartbeats, so the synchronous wait never looks
like a frozen prompt. Control-C preserves the implementation request and any
project changes; \texttt{workflow status} shows the interrupted state.
Interactive Codex sessions retain their ordinary terminal output.

There is no assistant queue or scheduled background job. The command runs
synchronously: before launch, \texttt{workflow status} says the implementation
is prepared and
\texttt{Execution: not started; nothing is scheduled}. A normal return
changes the same request to \texttt{implemented} and prints a bounded summary
of changed files, assistant checks, and the assistant report. Separately,
\texttt{Assistant checks} are \texttt{passed}, \texttt{failed}, or
\texttt{incomplete}, with a concise note and the number of checks the
assistant reported. The \texttt{workflow status} output lists each reported command and
its outcome underneath the summary. A missing, malformed, or internally
inconsistent handoff is never interpreted as success. A failed or interrupted
assistant process remains visible and retryable. If Studio or the computer
stops while the assistant is running, the orphaned state is recovered as
\texttt{assistant interrupted} on the next inspection. Studio refuses to rerun an
\texttt{implemented} request accidentally; use
\texttt{workflow implement codex --rerun} or
\texttt{workflow implement claude --rerun} only when a second pass is intentional.
Studio refreshes an older unexecuted task automatically before launch so that
it also receives this assistant-check contract.

\begin{lstlisting}[style=shell]
workflow status
Workflow implementation
  Status     [success] implemented
  Assistant            Codex -- returned ...
  Execution            assistant session ended; nothing is scheduled
  Assistant checks [success] passed -- 5 checks
  Check summary              Validation, projections, diff, and focused tests passed.
  Context    [success] implementation matches this task
  Next                  workflow diff / workflow validate / run / deploy
\end{lstlisting}

The checks below that summary are records rather than unbounded table values:

\begin{lstlisting}[style=shell]

----------------
5 checks / 5 passed / 0 failed / 0 not run

[success] 1. passed
  Command  uv run --offline --project zippergen zippergen validate
           workflows/reviewed_answer.py:reviewed_answer
  Result   Validated the global workflow and every local projection.
\end{lstlisting}

Studio preserves the complete command and result but wraps them with hanging
indentation. Assistant-check records are capped at 108 columns and use a narrower
interactive terminal width when necessary. A single long check therefore
cannot create a screen-wide separator. When assistant checks failed, failed and
unexecuted records are shown before successful checks.

The assistant-check result is an explicit assistant report, not an independent
proof. If it is \texttt{failed} or
\texttt{incomplete}, Studio shows that state prominently and proposes
inspection, validation, and an intentional assistant rerun instead of implying
that the change is ready. Immediately below the summary table it prints only
failed or unexecuted checks; the complete reported check list remains
available through \texttt{workflow status}. Use \texttt{workflow diff} to
inspect changes again and \texttt{workflow validate} for ZipperGen's technical
check of the project workflow.

The internal handoff retains a field named \texttt{verification} for its
versioned JSON contract. Studio presents it as assistant checks so it is not
confused with \texttt{workflow validate}. The summary works in non-interactive
sessions. Detailed inspection remains available through \texttt{workflow
diff}, \texttt{workflow show}, and \texttt{workflow status --details}.

If Studio says that \texttt{codex} is missing, the prepared task remains safe.
Open a second operating-system terminal. If npm is already installed, install
and authenticate Codex once:

\begin{lstlisting}[style=shell]
npm install --global @openai/codex
codex login
cd "$HOME/Projects/zippergen-tutorial"
codex
\end{lstlisting}

Then return to Studio and enter \texttt{workflow implement codex} again.
Section~\ref{sec:codex} explains setup for both supported assistants and the
no-assistant fallback in more detail. The task points
the assistant to
\path{zippergen/AGENTS.md} and the nested framework's workflow skill when the
skill is not installed at the parent project root. The long workflow
specification remains in \path{specification.md} rather than being pasted into
the assistant's terminal.

\begin{notebox}{What \texttt{workflow implement} is---and is not}
\texttt{workflow implement codex} and \texttt{workflow implement claude} are
small launchers for
the locally installed Codex CLI and Claude Code respectively. They do not send

approval policy, and tools. MCP is not required. Independently configured MCP

nor manages them. Integrations can also consume Studio's generated
implementation request directly.
\end{notebox}

Wait for the assistant to report generated source, focused tests, validation,
communication-only and full views, and projections for Requester, Writer, and
Reviewer. In an interactive Git project, Studio offers to commit the
specification, implementation files, \path{zippergen.lock}, and a manifest that
implementation changed. Its suggested message is editable. The commit is
limited to those related files and does not include unrelated staged work.
Studio never pushes. Decline if you want to inspect or commit the files

Then inspect the checkout in the ordinary terminal:

\begin{lstlisting}[style=shell]

git diff
\end{lstlisting}

Do not commit merely because code was generated. First complete the checks
below. If generation is unavailable or fails, continue with workflow discovery

\subsection{Discover and configure generated workflow source}

Return to the Studio terminal and enter:

\begin{lstlisting}[style=shell]
workflow list
workflow import workflows/reviewed_answer.py:reviewed_answer
workflow files
workflow show source
\end{lstlisting}

Studio displays the discovered workflows. Import the newly generated
reviewed-answer workflow by the displayed \texttt{PATH.py:NAME}. When the file
is already in the project, Studio copies nothing and only writes the entry to
\path{zippergen.toml}.
The configured entry may display an internal reference of the form
\texttt{PATH.py:NAME}: the suffix names the Python workflow object, not a
deployment. Inspect the authored Python before asking validation to judge it.
The commands have deliberately different jobs:

\begin{description}
  \item[\texttt{workflow list}] discovers top-level \texttt{@workflow} entry
        points from project source and lists their \texttt{PATH.py:NAME}
        references. This is source discovery, not validation.
  \item[\texttt{workflow import PATH.py[:WORKFLOW]}] copies an external
        workflow into the current project before configuration. It preserves paths
        relative to the external project root when that root has
        \path{pyproject.toml}, \path{zippergen.toml}, or \path{.git}. It also
        copies statically imported local Python modules and literal files named
        by deployment or assistant declarations. If the project already has a
        workflow, Studio shows the replacement and asks before overwriting
        different files or changing the manifest.
  \item[\texttt{workflow files}] lists the entry module, statically imported
        project-local Python modules, and declared resource files known to the
        project workflow.
  \item[\texttt{workflow show source}] displays the authored entry module.
        Use \texttt{workflow show source NUMBER} or a path printed by
        \texttt{workflow files} to inspect another listed file.
\end{description}

A workflow entry point need not occupy one file. It may import \texttt{@fragment}
definitions, actions, connectors, or helpers from other modules. Conversely,
one module may expose several top-level \texttt{@workflow} entry points.
Studio lists every discovered entry point as importable source, while the
manifest identifies exactly one as this project's workflow. Supporting files
are inspection material, not additional project workflows.

If no workflow entry is configured, \texttt{workflow show},
\texttt{workflow files}, \texttt{workflow edit code}, and
\texttt{workflow validate} perform this one-time setup automatically. One
discovered entry point is recorded with an explicit notice; several open the
numbered selector. In both cases Studio says that validation has not yet run.

\section{Workflow inspection and validation}

\subsection{Inspect increasing degrees of detail}

Enter \texttt{workflow show} and choose the semantic views:

\begin{lstlisting}[style=shell]
+----------------------------------------------------------+
| ZipperGen Studio : workflow show                         |
+----------------------------------------------------------+
1. Authored source
2. Overview
3. Protocol
4. Communications only
5. Actions and prompts
6. Complete workflow
7. One participant
8. Selected participants
\end{lstlisting}

Then use the direct forms:

\begin{lstlisting}[style=shell]
workflow show communications
workflow show actions
workflow show full
workflow show agent Writer
workflow show agent Reviewer
workflow show agents Writer Reviewer
connector
workflow validate
current
\end{lstlisting}

All results are code. \texttt{workflow show communications} hides local actions
and retains messages and control. \texttt{workflow show actions} reveals action
calls and prompts. \texttt{workflow show full} adds implementation and deployment requirements.
\texttt{workflow show agent Reviewer} is the exact projected local program.
\texttt{workflow show agents Writer Reviewer} is a focused global view with hidden
peers marked as boundaries; it is not a projection.
\texttt{connector} discovers the human-active participants and actions from
the workflow. Before an external route is assigned, it shows the local
terminal as their effective delivery path.

Only the final \texttt{workflow validate} command makes a validity claim.
Discovery answers which entry points exist, and selection answers which one is
being discussed. Validation additionally checks the global protocol, input
ownership, every local projection, action metadata, referenced resources, and
deployment declarations. Every successful check begins with a green check
mark; a red cross identifies a failure and is followed by its explanation.
\texttt{current} then shows the active workflow and execution context,
including the fresh validation summary, model routing, latest run, and selected
deployment. Use \texttt{project} when you want the complete project inventory.

\begin{notebox}{Validation and deployment answer different questions}
\texttt{workflow validate} checks the current code: is the global workflow
structurally valid, and can every participant be projected consistently? It
can be run repeatedly and does not change project state.

\texttt{deploy} checks a separate coherence property. Studio compares the
committed \path{zippergen.lock} record with the specification and generated
source. This derives \emph{absent}, \emph{stale}, \emph{current}, or
\emph{external}, including on a fresh clone. Deployment blocks \emph{absent}
and \emph{stale}. It warns and proceeds for \emph{external}, whose provenance
is unknown rather than known to disagree. Git remains the version history for
source and specification changes.
\end{notebox}

Inspect declared boundaries in proportion to their risk. A workflow with
human actions, external effects, assistant actions, or deployment metadata
deserves closer source and projection inspection. Model calls can transmit
data, and prompt changes can materially change behavior even when no
\texttt{@effect} is present.

Before running, confirm from these views who owns both inputs, who owns the
retry decision, whether every revision returns to human review, whether an
unapproved draft can reach Requester, whether both model prompts are visible,
and whether HumanApprover's human action is discoverable. Do not continue
until the code answers all six clearly.

If the connector view reports no human actions, inspect the full workflow.
The generated code is incomplete when the requested \texttt{@human} action is
absent. After implementation, use
\texttt{workflow implement codex --rerun} or the corresponding Claude command.
Record a requested correction with \texttt{workflow edit-refinement}, apply it
with \texttt{workflow refine-spec}, then implement the updated specification.

\section{Durable execution, recovery, and stores}

\subsection{Make a durable mock run in one terminal}

Enter \texttt{run}. Before asking for inputs, Studio checks every model
configuration that is actually used by an LLM-active participant and performs
technical workflow validation. A shared configuration is checked once. If a
provider is unreachable or the configured model is absent, Studio stops before
it creates the run and points to the relevant
\texttt{model config check} command. The run summary shows one effective
model route per LLM-active participant rather than only showing the default
fallback.

\begin{lstlisting}[style=shell]
zippergen [reviewed_answer]> run
Run model checks
...
Workflow reviewed_answer: valid
Request to answer (str) ["Explain why the sky is blue in two sentences."]:
Maximum revisions after the initial draft is rejected (int) [2]: 3
Run reviewed_answer-<timestamp>

Draft:
[draft_reply:draft]

Automated reviewer notes:
[assess_draft:concerns]

\end{lstlisting}

Press Enter for the displayed request, enter \texttt{3} for the retry budget,
\texttt{n} for the first review, and \texttt{y} for the second. The mock result
is a recognizable placeholder. The important behavior is a separate Writer
draft, Reviewer assessment, visible human authority, and another revision and
assessment after rejection.

Enter \texttt{current} and \texttt{runs}. Studio shows a unique managed SQLite
store even though no filename was typed. Every new \texttt{run} receives a new
store and never silently reuses an old result.

\subsection{Inspect current projected positions}
After an interrupted run, enter at the Studio prompt:

\begin{lstlisting}[style=shell]
run inspect
run inspect Reviewer
\end{lstlisting}

For a live foreground run, keep its terminal untouched and open another
terminal at the project root:

\begin{lstlisting}[style=shell]
zippergen
run inspect Reviewer --watch
\end{lstlisting}

The second Studio process performs read-only inspection. It refreshes the
positions once per second in one fixed terminal screen, without appending
repeated output. Its differential renderer updates only changed terminal
cells, so pointer movement does not clear and repaint the complete screen.
Press Ctrl-C to restore the Studio screen and return to its prompt. The
development run is not interrupted. For a single
non-interactive snapshot, use:

\begin{lstlisting}[style=shell]
zippergen studio --command "run inspect Reviewer"
\end{lstlisting}

The first process continues to own terminal input and any inline human
decision.
The first command reads the current development run's durable observation
rows and shows one participant per line. States distinguish running,
receive-blocked, human/model/assistant/effect activity, completion,
cancellation, and failure. Studio focuses the participant most likely to need
attention. Naming a participant focuses it explicitly and prints its exact
projected local program with one or more pointer markers. Multiple pointers
are possible inside a local parallel region.

This view has size proportional to the projected program, not the accumulated
trace: a hundred loop iterations move the same pointer instead of adding a
hundred message rows. Observation locators are deliberately separate from the
loop-boundary snapshots used for recovery. Studio also withholds local
environment values, action inputs, and secrets; use task presentation or
explicit trace inspection when those details are genuinely required.

\subsection{Work through the current development run}
Enter:

\begin{lstlisting}[style=shell]
run inspect
run tasks
run approve
run trace
\end{lstlisting}

\texttt{run inspect} shows the current participant positions and one focused
local projection. Bare \texttt{run approve} selects the sole pending task
automatically or opens a numbered selector when there are several.
\texttt{run tasks} renders each task's instruction and decision context, and
\texttt{run approve} repeats the complete context immediately before
collecting a response. For the reviewed-answer workflow, that context contains
the proposed draft and automated reviewer notes, so the human never approves
an opaque identifier. \texttt{run trace} shows recent durable events.

Studio creates a unique SQLite file for each development run. The file is an
implementation detail, not a separately selected or renamed Studio object.
The corresponding deployment commands operate on the one durable state owned
by a named deployment.

\subsection{Verify crash and resume behavior}

Start another run and press Control-C at the human prompt. Studio records the
managed run as interrupted and prints a recovery hint instead of a traceback.
The expected transition is:

\begin{lstlisting}[style=shell]
Approve this draft for the requester? [y/n]: ^C
Command interrupted. Use 'current' to inspect context; use 'resume' for an incomplete managed run.
zippergen [reviewed_answer]>
\end{lstlisting}

Only Studio's main thread reads the terminal. After the warning, no abandoned
workflow thread should consume a Studio command or print another approval
prompt. You may enter \texttt{current} and \texttt{resume} immediately;
\texttt{current} reports the run as interrupted, and \texttt{resume} presents
the same still-pending approval once. To test a full terminal or computer
restart, leave Studio, reopen a terminal later, and enter:

\begin{lstlisting}[style=shell]
cd "$HOME/Projects/zippergen-tutorial"
zippergen
current
resume
\end{lstlisting}

\texttt{resume} reuses recorded inputs, model routing, and SQLite state; the
pending task is presented again. It also checks the workflow's semantic
fingerprint. If source meaning changed, Studio preserves the store and refuses
an unsafe resume.

No export must be repeated. The workflow, model routing, run record, and
development secrets live below \path{$HOME/.zippergen/workspaces} by default.
A shell export disappears with its shell; Studio's workspace record does not.

The initial workflow has now been generated. Inspect its differences and run
the technical check:

\begin{lstlisting}[style=shell]
workflow diff
workflow validate
\end{lstlisting}

\texttt{workflow status} should say \texttt{implemented}. The implementation
summary already showed changed files, assistant checks, and the assistant's
report. \texttt{workflow diff} is the detailed inspection path, while
\texttt{workflow validate} independently checks structure and projection.

it in the provider console and create a replacement before continuing.

The model workflow has three deliberately separate layers:
\emph{provider, configuration, assignment}. A provider connection contains an
API key or local endpoint. A named configuration contains a provider and exact
model identifier. For a local Ollama model, it can also contain an idle-release
time. An assignment maps an LLM-active participant to one of those names.
Enter \texttt{model setup} for a guided pass through all three layers.

The provider and exact model identifier are project decisions. Named model
configurations and participant or action assignments are therefore written to
\path{zippergen.toml}. A local endpoint, idle-release policy, cached connection
checks, and API keys describe one machine and stay in private site state. A
site assignment can override the project route without adding another
precedence system:

\begin{lstlisting}[style=shell]
model assign Writer mock --site
\end{lstlisting}

The effective lookup has one rule: use the site override when it exists,
otherwise use the project value. Plain \texttt{model assign} edits the project
assignment. The \texttt{--site} form changes only this machine.

\texttt{model provider configure PROVIDER} asks for a missing API key without
echo, or for the endpoint of a local provider. It saves and checks the
connection. \texttt{model provider check PROVIDER} repeats that check later.
\texttt{model config create NAME} then asks for one configured provider and
one model identifier. It does not collect credentials: if the chosen provider
is not configured, Studio stops and prints the exact provider command to run
first. Plain \texttt{model} makes no remote request, never prints a secret,
and displays provider connections, named configurations, and workflow
assignments as separate tables.

\texttt{model config check} checks every saved configuration;
\texttt{model config check NAME} checks one. It records \texttt{available},
\texttt{unverified}, or \texttt{unavailable}, but never changes which
participant uses which model. A green result confirms that the provider
accepted the configured key and exact model identifier at check time. A yellow
result means connectivity prevented a conclusive answer.
\texttt{model assignments} displays the effective route of every LLM action,
its source, and its cached last-check state. It never contacts a provider.
\texttt{model assignments check} performs a fresh, targeted check of only
those effective configurations, deduplicating configurations shared by
several participants. \texttt{run} repeats that targeted check as a mandatory
preflight. For a local
OpenAI-compatible or Ollama endpoint,
\texttt{model provider configure local} asks for the endpoint (normally
\texttt{http://127.0.0.1:11434/v1}). A later
\texttt{model config create NAME} asks for the local model. Local identifiers
are checked against the live \texttt{/models} response. Studio also asks when
the local model should be released after its last call. The default is
\texttt{300} seconds. Enter \texttt{never} to keep it loaded, or
\texttt{0} to release it after every call. The workflow and its durable state
remain active. Ollama loads the model again automatically when the next LLM
action is reached. The policy follows the named configuration into development
runs and deployments. Hosted providers need no idle-release setting because
ZipperGen does not keep their models in local memory.

\texttt{model assign PARTICIPANT NAME},
\texttt{model assign PARTICIPANT.ACTION NAME}, and
\texttt{model default NAME} only assign saved configurations; they do not
contact the provider. Studio warns when a configuration has not yet been
checked but allows the assignment so offline preparation remains possible. A
configuration whose last conclusive check found it unavailable must be fixed or
checked successfully before assignment.
An action assignment takes precedence over its participant assignment, which
takes precedence over the default. Enter
\texttt{model inherit PARTICIPANT.ACTION} to remove one action override, or
\texttt{model inherit PARTICIPANT} to restore the project default for that
participant.
Append \texttt{--site} to any of these assignment commands to change only this
machine. A site assignment overrides the project assignment in one lookup. It
does not create an environment or another precedence layer.
Use Tab completion rather than retyping generated names. Editing one named
configuration with \texttt{model config edit NAME} updates every assignment
that refers to it. \texttt{model config rename OLD NEW} changes only its
reusable name: Studio preserves the provider, model, and recorded check result
and updates every default and participant assignment in the project atomically.
It does not reconnect to the provider or change runtime model selection.
\texttt{model config remove NAME} refuses to remove a configuration that is
still in use. \texttt{model provider remove NAME} removes a provider
connection and its privately stored key.

One named configuration may be assigned to any number of participants. They
share the provider/model settings, but not one stateful conversation, client
lock, or execution slot. Their LLM actions remain independent and can run in
parallel; the provider's own rate and concurrency limits still apply. The
model identifiers above are examples; use models enabled for your provider
accounts when necessary.

\begin{notebox}{Two different meanings of ``change the model''}
For a routing-only change, create or edit a named configuration, check it, then
use \texttt{model default NAME} or
\texttt{model assign PARTICIPANT NAME}. Studio remembers that choice for runs
and deployment; source code does not change, so no refinement or coding
assistant is needed. If the model choice must become versioned design intent,
change declared workflow/deployment defaults, or accompany prompt, action, or
test changes, record it as a refinement and run an assistant. For example:

\begin{lstlisting}[style=shell]
workflow edit-refinement Use openai:gpt-4o-mini for Writer and preserve all protocol behavior.
workflow refine-spec
workflow implement claude
\end{lstlisting}

The second form puts the instruction in one ignored scratch buffer. The
specification assistant sees only that buffer and the canonical specification.
Implementation remains a separate, deliberate command.
\end{notebox}

\section{Refinement and reimplementation}

\subsection{Refine through one scratch buffer}

Use \texttt{workflow edit-refinement} to describe one change, then apply it to
the specification:

\begin{lstlisting}[style=shell]
workflow edit-refinement "Require a second review after a rejected draft"
workflow refine-spec
workflow implement
\end{lstlisting}

The refinement lives at \path{.zippergen/refinement.md}. It is ignored by Git,
has no lifecycle, and is read only by \texttt{workflow refine-spec}. That
command runs the configured assistant in an isolated temporary directory with
only the current specification and refinement. The implementation is not
visible, so the specification cannot be fitted retroactively to existing code.
A successful revision consumes the buffer. Emptying the buffer discards it.

After the assistant returns, Studio prints an implementation summary with the
changed files, assistant-check result, and assistant report. The detailed
inspection commands remain available:

\begin{lstlisting}[style=shell]
workflow status
workflow diff
workflow validate
\end{lstlisting}

\texttt{workflow diff} compares the available specification and semantic
baseline. \texttt{workflow validate} is the independent structural and
projection check. If checks failed or were incomplete, inspect their details
with \texttt{workflow status --details} and rerun the assistant deliberately
with \texttt{workflow implement codex --rerun} or the corresponding Claude
command.

\texttt{workflow implement} writes \path{zippergen.lock} with the workflow
entry, specification fingerprint, generated-source fingerprint, and source
file list. Editing the specification makes a generated implementation
\emph{stale}. Editing generated source makes it \emph{external}. Stale source
blocks deployment. External source proceeds after a provenance warning and
technical validation. Git is the version history for returning to an earlier
source/specification pair. \texttt{workflow status} and \texttt{deploy} warn
when a file in this implementation unit is modified or uncommitted, because a
fresh clone may derive another implementation state. The warning is
informational and never blocks deployment. Studio performs no Git operation
outside the explicit post-implementation offer.


\section{Deployment and operation}

First prepare the named deployment without starting a background service. This
command snapshots the current working tree into an immutable bundle, creates a
separate deployment bundle and deployment-specific Python environment, writes
service definitions, and runs readiness checks. It changes files below
ZipperGen's private home but deliberately defers service-manager state. On the
tutorial machine, enter in Studio:

\begin{lstlisting}[style=shell]
deploy reviewed-answer-tutorial --no-start
\end{lstlisting}

Studio compares any local implementation fingerprint with the current
specification fingerprint. If the specification changed after implementation,
deployment stops with \texttt{workflow implement} as the remedy. If no local
record exists, Studio warns instead. In both cases Studio validates the
project workflow again before preparing the bundle.

A previously running deployment is
not reading the working tree: it continues to execute its own timestamped
bundle until an explicit deployment or restart changes its operational state.
This coherence check belongs to Studio. The lower-level operating-system command
\texttt{zippergen deploy PATH:WORKFLOW} remains an explicit expert interface
and does not consult Studio's implementation request.

Studio carries the current default, participant, and action routes into the deployment
profile. If the current model profile selects a real provider and its key was
configured earlier, Studio displays a \emph{Deployment credentials} summary
containing the key's name but never its value:

\begin{lstlisting}[style=shell]
Deployment credentials
  Available   [success] OPENAI_API_KEY in private Studio storage
  Deployment             reviewed-answer-tutorial
  Storage                separate private deployment secret file

Reuse the configured credential for deployment reviewed-answer-tutorial? [Y/n]:
\end{lstlisting}

Press Enter to reuse it. Studio copies the hidden value directly into the
deployment's separate mode-0600 file, so the guided deployer does not request
the key again. This applies to every selected OpenAI, Anthropic, or Mistral
route even if the workflow's deployment declaration did not explicitly name
that provider's key. Readiness refuses to start when a selected API model has
no deployment-scoped credential. Enter \texttt{n} only when this deployment
should use a different credential; the deployer then asks for that value
without echo. A later
\texttt{deploy reviewed-answer-tutorial} retains the deployment's existing key
and prints that it is keeping the saved value, without presenting another
secret prompt. A selected local configuration needs no key; Studio copies its
configured OpenAI-compatible endpoint into the deployment profile so that the
deployed service uses the same local or tunneled server as development. With
the recommended \texttt{model default mock} and
\texttt{model inherit} commands above, all routes are mock and no provider
key is needed.

Read every prompt. The request and retry budget are runtime inputs, not another
description of the workflow. A successful ending prints
\texttt{Deployment: reviewed-answer-tutorial} and leaves the service stopped.
Studio remembers the deployment name. Check the prepared artifacts before the
first real service-state change:

\begin{lstlisting}[style=shell]
deploy doctor
deploy show
\end{lstlisting}

\texttt{deploy show} separates four objects that must not be confused:
the immutable bundle, the supervised operating-system process, the workflow
run, and its SQLite store. Studio condenses the deployer's checks into one
readiness summary; \texttt{deploy doctor} is the explicit expanded view.
Doctor should contain no failures. Deployment preparation initializes the
stable store, even with \texttt{--no-start}. Before first execution, that
store is ready and empty, while a missing log and an uninstalled service are
expected warnings. If the checks are acceptable and service startup is
authorized, enter these one at a time:

\begin{lstlisting}[style=shell]
deploy start
deploy show
deploy inspect
deploy inspect Reviewer
deploy inspect Reviewer --watch
deploy tasks
deploy approve
deploy logs
deploy restart
deploy show
deploy stop
deploy storage
deploy storage compact
\end{lstlisting}

\texttt{deploy start} is the first command here that changes
service-manager state. It reruns readiness checks immediately before doing so;
\texttt{deploy start} in Studio also enables persistent automatic startup.
The \texttt{Boot} row of \texttt{deploy show} states whether the deployment
will start at server boot, after the user logs in, or only after a manual
start. On Linux, automatic startup at server boot requires both an enabled
systemd user service and account lingering. Studio reports these separately
because enabling a deployment does not grant permission to change the
server's account policy.
\texttt{deploy restart} applies the same gate. A failed credential,
workflow import, bundle, package, or workflow-specific doctor check blocks the
operation before launchd/systemd is touched. Warnings remain informative and
do not block startup. \texttt{deploy stop} is never subject to this gate.
The process may need a few seconds to reach its first action; repeat
\texttt{deploy show} once if necessary. The run/store rows should report
\texttt{waiting} once durable human approval is pending. Immediately after
\texttt{deploy start}, the run may briefly report
\texttt{starting, no durable events recorded yet}. The separate store row
remains ready. Each deployment name owns one stable logical store, so normal
deployment operation requires no store selection or copied path.
\texttt{deploy inspect} reads per-participant positions from that store
and projects the workflow from the immutable deployment bundle, so later
working-tree edits cannot change what is displayed. With no name it uses the
remembered deployment; a participant can be supplied as the final argument.
Add \texttt{--watch} to refresh the positions and focused projection once per
second. Ctrl-C closes only the live view and does not stop the deployment.
\texttt{deploy tasks} shows the full
stored instruction, draft, reviewer notes, and decision labels;
\texttt{deploy approve} repeats them immediately before accepting yes or
no. \texttt{deploy trace} shows recent durable events without requiring a
SQLite path.
\texttt{deploy storage} shows the store, WAL, logs, event counts, recovery
snapshot coverage, and the amount of history that can be removed safely. It
first runs SQLite's structural quick check. The explicit
\texttt{deploy doctor} command runs the same check and reports a failure if the
store is malformed. Normal start and restart readiness checks do not rescan a
large healthy store.
Diagnostic traces are pruned online in batches. The target is 10,000 traces
and the store never keeps more than 10,999. This requires no service stop.
Completed human tasks, tokens, and notifications remain as audit records.
\texttt{deploy logs} shows the service output and returns;
\texttt{deploy logs reset} archives the currently visible history and begins
a fresh logical log generation without stopping the service or changing its
workflow run and durable store. Studio asks for confirmation and reports the
private archive path. New output continues in the active log normally.
\texttt{deploy storage compact} is the durable cleanup command. Stop the
deployment first. It deletes only completed communications and journal entries
covered by durable recovery floors, rotates the active log, and keeps three
log archives.
Participants without a recovery snapshot are named and block core event
cleanup for the events they still need. Trace retention runs independently
while the service is online.
Studio then compacts the database file and truncates the WAL while preserving
the stable event identifiers used for recovery.
Deployments created before this feature must be redeployed once before safe
compaction is enabled. Studio reports this instead of touching an older
runtime bundle.

\begin{warningbox}{Keep durable stores private and on local storage}
ZipperGen creates a store with owner-only mode \texttt{0600}, uses WAL, and
explicitly requests \texttt{synchronous=FULL} on every durable protocol writer
connection. The store must remain on a local filesystem with reliable SQLite file locking and
\texttt{fsync}. Do not put it on NFS, a synchronized folder, or a remote
container volume whose SQLite guarantees are unknown. Do not edit rows with a
SQL client.

The quick check finds structural database damage. It cannot detect a row that
was deliberately deleted from an otherwise valid database. Compaction is the
only supported row-deletion path. It uses participant recovery floors and may
legitimately remove completed rows. Therefore, an always-increasing row count
is not a valid integrity test.
\end{warningbox}

The alpha does not yet have a managed restore command. To make a consistent
online backup, take the store path from \texttt{deploy storage}, choose an
owner-private destination, and use SQLite's backup command:

\begin{lstlisting}[style=shell]
mkdir -p "$HOME/.zippergen/backups"
chmod 700 "$HOME/.zippergen/backups"
(
  umask 077
  sqlite3 "/PATH/TO/DEPLOYMENT.sqlite" \
    ".backup '$HOME/.zippergen/backups/DEPLOYMENT.sqlite'"
)
\end{lstlisting}

This backup may be taken while the deployment runs. Do not restore it by
copying over a live store. A backup contains workflow data and human approval
tokens, so keep it mode \texttt{0600} and outside Git. A future managed restore
flow will stop the service, verify the backup, archive the current store, and
state the recovery window before replacement.

Restoring an older store can repeat external work that succeeded after the
backup but whose journal entry is absent from the backup. This includes model
calls, email sends, sheet appends, and other \texttt{@effect} or connector
operations. Use stable idempotency keys or idempotent remote operations whenever
duplicates matter.
\texttt{deploy restart} deliberately proves that the same
pending task survives a process restart. Then \texttt{deploy stop} prevents this
finite tutorial workflow from being supervised indefinitely. Later chapters
show task tokens and notification adapters for delivering the same approval
context through Telegram or another out-of-process channel. Stopping does not
delete the profile, bundle, log, secrets, or store.
The generated launchd/systemd service retries failures but does not relaunch a
finite workflow after successful completion.

If Studio reports that no supported user service manager is available, stop at
the error and use the later \texttt{deploy --no-start} plus
\texttt{run-deployment} foreground path. Do not repeatedly retry a failing
service start without reading \texttt{deploy doctor} and
\texttt{deploy logs}.

\begin{warningbox}{Deployment is a real operational action}
First complete mock execution and inspect \texttt{workflow show full}. A real model call
may cost money and an \texttt{@effect} may change an external system. Use fake
services until effects and retry safety have been reviewed.
\end{warningbox}

normal Studio prerequisite.

\subsection{Start from a prompt, or refine an existing workflow}

For a multiline description, let Studio open the canonical project document:

\begin{lstlisting}[style=shell]
workflow edit-spec
\end{lstlisting}

For a short idea, provide the description on the same line:

\begin{lstlisting}[style=shell]
workflow edit-spec Draft an answer and require human approval.
\end{lstlisting}

Studio saves a structured coding-assistant task. It asks for visible Python
source, focused mock/fake tests, validation, communication and full views,
exact participant projections, and no deployment. The stable generated mirror
is \path{.zippergen/current-task.md}, which is ignored by Git; timestamped
archives remain outside the checkout.

\begin{notebox}{Current assistant boundary}
Studio's \texttt{workflow implement codex} and \texttt{workflow implement
claude} commands launch the selected local coding tool on the current
implementation request. Neither is a ZipperGen
workflow model provider, and neither automates deployment. The assistant edits
ordinary files in the checkout; ZipperGen then loads, validates, projects,
renders, and runs the result. Integrations can consume the same generated
request directly. After hand-written source creation, enter \texttt{workflow
list} and \texttt{workflow import PATH.py:NAME} to discover and record the
workflow in the manifest. The request
is not a queued job: Studio records the synchronous assistant return as
\texttt{implemented}, then prints the changed files, assistant checks, and
assistant report. Use \texttt{workflow diff} and \texttt{workflow validate}
for detailed inspection.
\end{notebox}

For an existing project workflow, write a scratch refinement and apply it:

\begin{lstlisting}[style=shell]
workflow edit-refinement
workflow refine-spec
\end{lstlisting}

Studio owns both filenames. The specification assistant sees only the canonical
specification and scratch refinement in an isolated directory. It rewrites
\path{specification.md} and consumes the buffer. Run
\texttt{workflow implement} afterward to update code and tests.

\subsection{Use a real LLM without repeating an API-key export}

Remain on the mock backend until the complete local path works. First follow
the account, billing, key-creation, and revocation precautions in the
real-model readiness section. When ready, configure one model for Writer and
another for Reviewer:

\begin{lstlisting}[style=shell]
model provider configure openai
model config create drafting
model config check drafting
model assign Writer drafting
model provider configure anthropic
model config create careful-reviewer
model config check careful-reviewer
model assign Reviewer careful-reviewer
model
run
\end{lstlisting}

Studio remembers the named configurations and assignments per workflow.
Provider setup collects each key first; configuration creation then asks for
the exact model. Enter each requested key without echoing its value:

\begin{lstlisting}[style=shell]
OPENAI_API_KEY:
Provider [openai]:
Model identifier [gpt-4o-mini]:
ANTHROPIC_API_KEY:
Provider [anthropic]:
Model identifier [claude-sonnet-4-6]:
\end{lstlisting}

The secrets are stored once below
\path{$HOME/.zippergen/workspaces/<project>/}, in a file named
\path{development.secrets.json} with owner-only mode-0600 permissions. Later
runs and post-crash resumes reuse it.
The values are not copied into \path{workspace.json}, a run record, an assistant
brief, source code, or Git. Values already supplied by the process environment
are used temporarily but are not copied into the private file.

This is lightweight local secret storage, not an operating-system keychain or
enterprise secret manager. Deployment secrets are scoped separately. When a
selected real provider has a matching key in private Studio storage, the first
deployment explicitly offers to reuse it. Pressing Enter accepts the default;
Studio transfers the hidden value directly into that deployment's own private
mode-0600 secrets file. It never displays the value or puts it in project
state. Answering \texttt{n} preserves the option to enter a distinct deployment
credential. A later deployment with the same name keeps its already-saved
deployment key without asking for it again.

\section{Studio language, settings, and editors}
\label{sec:studio-preferences}

These controls are useful after the first workflow succeeds, but none is a
prerequisite for writing its specification. Studio's exact commands remain the
durable, scriptable interface; ordinary language is a discoverability layer
that always exposes the resulting command plan.

\subsection{Commands and ordinary language}

At the Studio prompt, requests such as the following use the deterministic
interpreter and need no model, network, or API key:

\begin{lstlisting}[style=shell]
What is the current state?
Show me the whole protocol.
Assign the mock model to Writer.
Please restart ZipperGen Studio.
\end{lstlisting}

They become \texttt{current}, \texttt{workflow show protocol},
\texttt{model assign Writer mock}, and \texttt{studio restart}. Studio prints
the exact plan before its result. Starting or stopping execution, deployment
operations, and destructive changes require confirmation. Use
\texttt{plan TEXT} to preview an interpretation without executing it and
\texttt{ask TEXT} to request interpretation and execution explicitly.

If unmatched declarative or imperative prose might describe the application,
Studio offers to treat it as a workflow requirement. Before
\path{specification.md} exists it proposes \texttt{workflow edit-spec}; afterward
it proposes \texttt{workflow edit-refinement}. The offer does not depend on framework
words such as ``workflow'' or ``participant''. Enter \texttt{y} to store the
requirement, \texttt{n} to cancel, or \texttt{command} to interpret the same
sentence as an operation without changing the specification. Questions and
recognizable operational or troubleshooting requests remain on the command
path. Explicit \texttt{ask TEXT} and \texttt{plan TEXT} bypass the requirement
offer.

Short phrases use project context: \texttt{run it} means the project workflow
and \texttt{stop it} means the remembered deployment. Ambiguous
\texttt{start over} asks whether the intention is a new run, specification
change, Studio restart, or fresh project design. The unambiguous
\texttt{reset everything} proposes the recoverable fresh-design reset.

When repository details are required and no built-in or learned
interpretation matches, Studio may run an already authenticated Codex or
Claude Code CLI once. It receives non-secret, read-only project context and
may return only a structured plan made from documented Studio commands.
Studio validates and executes the plan itself; model text is never run as
shell code.

\subsection{Global settings and project-local learning}

Inspect and change the language layer with:

\begin{lstlisting}[style=shell]
settings
settings set learning on
settings set interpreter auto
settings set assistant codex
settings set editor micro
settings set output banner
language
language set auto
language set codex       # or: language set claude
language history
language learned
language forget L001
\end{lstlisting}

\texttt{settings} contains owner-private preferences shared by every local
ZipperGen project: learning policy, interpreter, default coding assistant,
editor, and output style. It is stored below
\path{$ZIPPERGEN_HOME/settings.json}. Learning policy is global, but learned
interpretations and command history are project-local, so one project cannot
silently teach another.

\texttt{auto} prefers Codex and then Claude for a repository-aware fallback
and reuses the CLI's own login; no ZipperGen model-provider key is involved.
\texttt{language set off} retains deterministic and already learned
interpretations without launching a CLI. After a successful CLI plan, Studio
stores the accepted request, structured commands, and outcome in owner-private
project state and can generalize recognized values such as participant names.
Use \texttt{settings set learning off} to stop adding entries globally, or
\texttt{language forget ID|all} to remove entries from the current project.

Raw CLI output is not learned. Secret-looking requests are rejected before
interpretation and are not stored. Provider credentials belong in the private
prompt opened by \texttt{model provider configure}.

\subsection{Automatic and explicit terminal editors}

Studio checks an explicit preference, then \texttt{\$VISUAL} and
\texttt{\$EDITOR}, then installed \texttt{micro}, \texttt{nano},
\texttt{vim}, and \texttt{vi}. Inspect the result or save a global preference:

\begin{lstlisting}[style=shell]
editor show
editor set micro
editor show
editor reset
\end{lstlisting}

\texttt{editor set nano} is equally valid and aliases
\texttt{settings set editor nano}. The choice is machine-specific Studio
state, not workflow source, and survives terminal closure and reboot.
\texttt{editor reset} restores automatic discovery.

An editor temporarily takes over the same terminal. Save and exit to return to
the unchanged Studio session. Studio launches the executable directly; it
does not invoke an LLM, shell script, provider, or MCP server. Override the
editor for one operation without changing the saved preference:

\begin{lstlisting}[style=shell]
edit file workflows/reviewed_answer.py --editor nano
workflow edit-spec --editor micro
\end{lstlisting}

For a command with arguments, quote the complete value, for example
\texttt{--editor "code --wait"}. Studio accepts edited files only inside the
project root and stops when the editor reports failure.

\section{The development-to-deployment boundary}

Deployment may install packages, run declared setup such as OAuth, create a
source bundle and managed environment, and start a macOS or Linux user service.
It is therefore always a separate, explicit command. With the tutorial still
selected, return to mock unless a real deployment is intentional, then choose
a separate name:

\begin{lstlisting}[style=shell]
model default mock
model inherit Writer
model inherit Reviewer
deploy tutorial-review-studio --no-start
\end{lstlisting}

The same guided deployer described later carries the current default and
participant and action model routes, collects declared settings and deployment-scoped
secrets, validates readiness, and prints the resulting deployment name. If a
selected provider key is already configured, Studio first shows only its
environment-variable name and asks whether to reuse it; accepting avoids
another secret-entry prompt while retaining a separate deployment copy. The
\texttt{--no-start} flag prepares the bundle and deployment environment without
installing or starting a user service. After a successful preparation, Studio
remembers that name. Inspect it first:

\begin{lstlisting}[style=shell]
deploy doctor
deploy show
\end{lstlisting}

The deployment store is already initialized and should be reported as ready
with no run data. Warnings about a missing first-run log and an uninstalled
service are expected at this point; a doctor failure is not. Only when service
startup is intentional and authorized, enter:

\begin{lstlisting}[style=shell]
deploy start
deploy show
deploy tasks
deploy logs
deploy restart
deploy show
deploy stop
\end{lstlisting}

\texttt{deploy start} is the first command in this sequence that changes
the user service manager. \texttt{deploy logs} returns after showing
recent output; it does not stop the service. \texttt{deploy stop} leaves
the deployment artifacts and durable store in place. To retire the complete
deployment safely, use:

\begin{lstlisting}[style=shell]
deploy remove tutorial-review-studio
\end{lstlisting}

Studio previews the service state and exact owned paths before it changes
anything. The default form stops and unregisters the service. It then moves
the profile, private secrets, generated launch files, bundles, managed
environment, stable store, SQLite sidecars, and log into a private archive
below \path{ZIPPERGEN_HOME/trash/deployments}. The deployment disappears from
\texttt{deploy list}. Project source, specifications, implementation history, shared
model configurations, and shared connector configurations remain. The archive
preserves the files for manual recovery. Studio does not currently provide an
automatic restore command.

For deliberate permanent cleanup, use
\texttt{deploy remove tutorial-review-studio --purge}. This form requires an
explicit deployment name. Without \texttt{--yes}, Studio also requires you to
type that exact name. There is no remove-all form. Permanent purge has no
recovery archive.

You may also provide a deployment name explicitly:

\begin{lstlisting}[style=shell]
deploy show tutorial-review-studio
\end{lstlisting}

The scriptable equivalents outside Studio remain
\texttt{zippergen status tutorial-review-studio} and so on.

\begin{warningbox}{Deployment is a real operational action}
Do not enter \texttt{deploy}, \texttt{deploy start}, or
\texttt{deploy restart} merely to
explore the menu. Read the deployment chapters first, remain on mock/fake
services, and understand the declared setup and effects. The \texttt{workflow show full}
view exposes prompts and deployment requirements before this transition.
\end{warningbox}

\section{Moving a workflow to a server}

\texttt{deploy} installs a service on the machine Studio is running on. There is
no remote deployment command. A server deployment therefore begins with a step
that is easy to overlook: the workflow source has to reach the server, and
Studio has to run there. This section covers that step. Everything earlier in
this chapter then applies unchanged on the server itself.

\subsection{Clone for ongoing work, import for a single file}

Two arrangements work. Prefer the first for any workflow you will change again.

Keep the workflow in a repository, clone it on the server, and use the clone as
the project root. Updates are then an ordinary \texttt{git pull}, and no import
or workflow-selection step is required at all. The versioned
\path{zippergen.toml} names both \path{specification.md} and the project's
workflow entry point:

\begin{lstlisting}[style=shell]
git clone git@github.com:you/your-workflows.git ~/workflows
cd ~/workflows
zippergen studio
\end{lstlisting}

Use \texttt{workflow import} when you want to pull one external file into an
existing project --- a shipped example, or a workflow kept outside the
repository:

\begin{lstlisting}[style=shell]
scp -r ./call-intake user@server:~/staging/
\end{lstlisting}

Then, in Studio on the server:

\begin{lstlisting}[style=shell]
workflow import ~/staging/call-intake/call_intake.py:call_intake
\end{lstlisting}

If that project already has a configured workflow, Studio shows the current
and incoming entry points, lists how many files differ, and asks before
replacing anything. A path already inside the project is adopted without a copy.

\subsection{Copy the directory, not only the entry file}

A workflow may name local files in its declarations: connector configuration,
prompt text, or data an action reads. \texttt{workflow import} reads the source
and copies those files together with the entry module. A manual \texttt{scp} of
one \texttt{.py} file does not. When you copy by hand, copy the directory that
contains the workflow rather than the file alone.

\subsection{Credentials stay on the machine that created them}

Copying a project directory moves no secret. Provider keys, connector tokens,
and Google credentials are stored below \path{ZIPPERGEN_HOME/workspaces} with
owner-only permissions, outside the project directory. A project directory can
therefore be copied, pushed to a repository, or handed to somebody else without
carrying credentials with it.

Named model and connector configurations, their assignments, and connector
bindings live in \path{zippergen.toml}, so they travel with the project. After
the source arrives, enter \texttt{project}. Its \emph{Site setup} branch lists
only the machine-specific facts and secrets that are still missing. Supply
those items, rather than reconstructing the design:

\begin{lstlisting}[style=shell]
project
model provider configure PROVIDER       # only when listed
connector provider configure PROVIDER   # only when listed
\end{lstlisting}

For example, a local model endpoint, API key, Telegram bot token, or Google
authorization remains private to the server. The model name, spreadsheet,
Gmail query, and participant routing are already present in the clone. A
private site override may replace a project model assignment on one machine;
otherwise the project value is used directly.

The implementation relationship is portable. Commit \path{zippergen.lock}
with the specification and generated source. A fresh server derives the same
\emph{current}, \emph{stale}, or \emph{external} state without private Studio
data. Deployment blocks \emph{stale}, but warns and proceeds for
\emph{external}. The post-implementation Git offer creates this local commit
as one unit. If you decline it and leave one of these files uncommitted,
\texttt{workflow status} and \texttt{deploy} warn before you copy or deploy a
working tree that another clone cannot reproduce.

\subsection{Validate on the server before deploying}

Run the ordinary inspection commands once on the server before the first
deployment. They load the module in that environment and fail early if a
resource file did not arrive or an import does not resolve there:

\begin{lstlisting}[style=shell]
workflow validate
workflow show
\end{lstlisting}

Only then supply the reported site facts, run the model and connector checks,
and continue with \texttt{deploy}.

\begin{notebox}{The same Studio, different commands}
Studio behaves identically on both machines. Authoring commands such as
\texttt{ask}, \texttt{plan}, \texttt{workflow refine-spec}, and
\texttt{workflow implement} use a coding assistant. Validation, running,
deployment, and inspection do not invoke that assistant.
\end{notebox}

\section{How to use the detailed reference}

The preceding topical chapters describe the recommended practical cycle. The

\begin{enumerate}
  \item Install an isolated Python environment for ZipperGen.
  \item Open the running example in Studio and discover the available

  \item Run a three-participant workflow with the built-in mock LLM.

\section{Conventions and safety}

\subsection{How to read commands}

All shell commands appear in boxes such as this:

\begin{lstlisting}[style=shell]
zippergen --help
\end{lstlisting}

Do not type a leading dollar sign if another document uses one to represent the
shell prompt. Run commands one at a time and read their output before moving on.
Unless a section says otherwise, run commands from the tutorial project root---
the directory containing \path{zippergen.toml}, \path{specification.md},
\path{workflows}, and the nested \path{zippergen} framework checkout.

Text such as \placeholder{TASK-ID} is a placeholder. Replace the complete
placeholder, including angle brackets, with the value printed on your machine.

There are three places where text is entered:

\begin{tabularx}{\linewidth}{p{0.18\linewidth}p{0.27\linewidth}X}
\toprule
\textbf{Place} & \textbf{Prompt usually visible} & \textbf{Examples} \\
\midrule

  \item \textbf{Terminal B} checks status and approves or rejects the task.
\end{itemize}

For those later examples, both terminals must be in the project root and

\section{Assistant actions and connector boundaries}

\subsection{Coding assistants inside an executing workflow}

The Studio command \texttt{workflow implement codex} is a development command: it asks
an assistant to edit the current project. The \texttt{@assistant} decorator is
different. It declares repository-aware assistant work as an explicit action
inside the protocol. The owning lifeline, typed inputs, static instruction,
result, trace event, and semantic change therefore remain visible.

\begin{lstlisting}[language=Python]
from zippergen import Lifeline, assistant, workflow

Maintainer = Lifeline("Maintainer")

@assistant(
    instructions_file="prompts/update_release_notes.md",
    access="write",
    external_tools="none",
    shell="restricted",
    workspace=".",
)
def update_release_notes(change: str) -> str: ...

@workflow
def maintain(change: str @ Maintainer) -> str:
    Maintainer: report = update_release_notes(change)
    return report @ Maintainer
\end{lstlisting}

Use exactly one of \texttt{instructions=} and
\texttt{instructions\_file=}. A Markdown path is relative to the project,
fingerprinted by semantic inspection, checked by \texttt{validate}, and copied
automatically into a guided deployment bundle. Function parameters are
dynamic workflow data and are passed separately from that static instruction.

\begin{lstlisting}[language=bash]
zippergen run workflows/maintain.py:maintain \
  --assistant codex \
  --input 'change=Document the new retry policy.'
\end{lstlisting}

\texttt{--assistant claude} selects Claude Code instead. Python callers may
select a CLI or inject a custom backend:

\begin{lstlisting}[language=Python]
workflow.configure(assistant="codex")
workflow.configure(assistant_backend=my_backend)
\end{lstlisting}

A Studio run uses \texttt{run --assistant codex}; that selection is recorded so
\texttt{resume} retains it. A recorded SQLite result is replayed without
launching the assistant again.
Nevertheless, make the requested file operation safe to resume: a crash can
occur after files change but before the action result is recorded.

Access is part of the action's reviewed semantics. The safe default is
\texttt{access="read-only"}; use \texttt{access="write"} explicitly for an
implementation action. ZipperGen maps the policy to the selected CLI's
non-interactive sandbox or permission mode; a prompt that merely asks a
reviewer not to edit is not the security boundary.

Filesystem access and external-tool access are separate capabilities. The
default \texttt{external\_tools="none"} disables configured MCP servers,
dedicated web tools, assistant subagents, and comparable integrations. Use
\texttt{external\_tools="configured"} only when the reviewed action
intentionally needs the user's configured tools.

Shell capability is a third reviewed policy. The default
\texttt{shell="restricted"} selects the strongest practical boundary offered
by each backend:
\begin{itemize}
\item Codex retains command execution inside its read-only or workspace-write
sandbox. When external tools are disabled, network access is disabled
structurally as well. Strict configuration parsing makes an unsupported
isolation key fail the action instead of being ignored.
\item Claude receives no Bash tool. Setting \texttt{shell="enabled"} permits
Bash, but Claude does not then provide Codex's structural network isolation;
\texttt{validate} displays a warning.
\end{itemize}

For a provider-independent hard boundary, let the assistant edit without a
shell and perform a predetermined check in a subsequent visible
\texttt{@effect}. The effect should contain a fixed executable and fixed
arguments; never execute a command string returned by the assistant. Arbitrary
shell access with provider-independent network isolation requires an external
operating-system or container sandbox.

Access, external-tool policy, and shell policy always appear in semantic
snapshots and diffs. Validation also warns when a write workspace contains the
executing workflow. That workspace permits self-modification, so the static
instruction must protect the running workflow and must not silently authorize
deployment, service control, commits, pushes, or unrelated external mutations.

The shipped
\path{examples/codex_claude_review.py} workflow demonstrates a bounded
Codex--Claude loop: Codex owns every repository change, Claude reviews
read-only after each candidate, success requires Claude approval, and Codex
produces the final read-only assessment.

\subsection{Connector providers, configurations, and assignments}

Human authority remains visible in workflow code as an \texttt{@human}
action. Its delivery mechanism does not belong in that code. Studio discovers
the owning participant and supports the same three-stage lifecycle as models:

\begin{lstlisting}[style=shell]
connector provider configure telegram
connector provider check telegram
connector config create telegram-approvals
connector config check telegram-approvals
connector assign HumanApprover telegram-approvals
connector assignments
connector assignments check
\end{lstlisting}

The provider owns private authentication, such as a Telegram bot token. A
named configuration chooses a reusable resource, such as one Telegram chat.
An assignment routes compatible actions to that configuration. The token is
stored outside the repository. Deployment copies only routing metadata into
the ordinary profile and places the credential in its private secret file.

A participant assignment covers every human action on that lifeline:

\begin{lstlisting}[style=shell]
connector assign HumanApprover telegram-approvals
\end{lstlisting}

An exact action may override it:

\begin{lstlisting}[style=shell]
connector assign HumanApprover.approve_contract legal-approvals
connector inherit HumanApprover.approve_contract
\end{lstlisting}

Several participants may share one configuration. Sharing a bot and chat does
not serialize their workflow steps. Every durable human task has an opaque,
one-time token. Telegram callback buttons include that token and the selected
option. A delayed, duplicate, or out-of-order external message therefore
cannot be mistaken for the next FIFO message. A numbered text answer is
accepted only when its task is identified by the token or by a direct reply to
the original Telegram message.

The deployed service starts its connector bridge automatically:

\begin{lstlisting}[style=shell]
deploy tasks
deploy show
\end{lstlisting}

No manual notification synchronization command is required. The bridge watches
the deployment's unique store, sends unseen tasks, consumes replies, and
completes exactly the corresponding durable action. A development run starts
the same bridge automatically when the project workflow has an external
human assignment. Without such an assignment, development keeps the human
decision in the Studio terminal.

Non-human services remain explicit workflow capabilities. Gmail and Google
Sheets use the same provider and configuration surface. Docs and Calendar can
follow the same pattern. A workflow declares a logical requirement and binds
that requirement to a saved resource configuration. Human delivery continues
to use participant and action assignments.

\subsection{Google Sheets resources}

Google support is optional so that a basic ZipperGen installation remains
small. In a source checkout, install it once with:

\begin{lstlisting}[style=shell]
uv sync --extra google
\end{lstlisting}

For an installed package, use
\texttt{pip install "zippergen[google]"}. Studio reports this exact command if
the support is missing. A managed deployment whose workflow declares Gmail or
Google Sheets installs the optional support automatically.

The workflow owns the meaning of a table operation. It declares the logical
table, columns, stable key, and whether an effect reads or writes data. It does
not contain a spreadsheet ID or OAuth token:

\begin{quote}
Records owns a project-records table with record\_id, title, and status
columns. One effect upserts a JSON record by record\_id. Another effect reads
all rows into a JSON workflow variable. Both effects use a required
read-write Google Sheets connector. Keep the spreadsheet and Google account
as deployment configuration.
\end{quote}

A repository-aware assistant can translate that requirement into the visible
workflow declaration and effects below:

\begin{lstlisting}[style=python]
import json

from zippergen import (
    ConnectorRequirement,
    Json,
    effect,
    read_json_rows,
    upsert_json_row,
)

zippergen_connectors = (
    ConnectorRequirement(
        name="project-records",
        kind="google-sheets",
        participant="Records",
        capabilities=("read-rows", "upsert-row"),
        access="read-write",
    ),
)

COLUMNS = ("record_id", "title", "status")

@effect(
    connector="project-records",
    operation="upsert-json-row",
)
def write_record(record: Json) -> str:
    return upsert_json_row(
        "project-records",
        json.dumps(record, sort_keys=True),
        columns=COLUMNS,
        key_field="record_id",
    )

@effect(
    connector="project-records",
    operation="read-json-rows",
)
def read_records() -> Json:
    return json.loads(
        read_json_rows(
            "project-records",
            columns=COLUMNS,
        )
    )
\end{lstlisting}

The stable key is important. Durable execution can retry an effect after a
process failure. A blind append could create the same row twice. The upsert
checks the key and replaces the existing row when needed.

The \texttt{Json} coordination type keeps the record structured inside the
workflow. It accepts ordinary Python values made from \texttt{None}, booleans,
numbers, strings, lists, and dictionaries with string keys. ZipperGen validates
the full nested value before durable execution and preserves it across
messages, crashes, and resume. The Google helper still receives JSON text at
the external API boundary. Arbitrary Python objects and pickle data are not
accepted as workflow variables.
Lists and dictionaries must be ordinary built-in containers, not subclasses.

The user configures the environment after selecting the workflow:

\begin{lstlisting}[style=shell]
connector setup
\end{lstlisting}

Google requires one account-level preparation before Studio can authorize the
connector:
\begin{enumerate}
  \item Create or select a project in Google Cloud Console.
  \item Enable the Google Sheets API for that project.
  \item Configure the OAuth consent screen for the intended test users or
        organization.
  \item Create an OAuth client with application type \emph{Desktop app}.
  \item Download its JSON file. Keep it outside the project repository.
\end{enumerate}

For a workflow with one Google Sheets requirement, guided setup performs these
steps:
\begin{enumerate}
  \item On a computer with a browser, it asks for the OAuth Desktop app JSON
        path and opens Google authorization directly.
  \item In an interactive SSH session without a browser, it prints one
        \texttt{uvx} command. Run that command on your own computer, not on
        the server. It needs no local ZipperGen installation. Copy the whole
        \texttt{zg-google-v1.}\ line it produces into Studio's hidden prompt.
        No file upload or SSH tunnel is needed.
  \item It asks for a spreadsheet URL or ID and a tab name.
  \item It checks that the spreadsheet and tab are reachable.
  \item It binds the saved configuration to the logical requirement.
\end{enumerate}

The equivalent explicit commands are:

\begin{lstlisting}[style=shell]
connector provider configure google
connector provider check google
connector config create project-records
connector config check project-records
connector bind project-records project-records
connector assignments check
\end{lstlisting}

The provider stores the authorization privately. It does not store the OAuth
client file or retain a user-managed client-file path. The configuration
stores only the spreadsheet ID and tab. The workflow binding stores only the
configuration name. During deployment, ZipperGen copies the resource metadata
into the immutable deployment profile and copies the OAuth credential into
the deployment's private secret file.

Studio derives Google scopes from each connector's declared
\texttt{access}. A read-only Sheets requirement requests
\texttt{spreadsheets.readonly}. A write or read-write requirement requests
\texttt{spreadsheets}. Google does not provide a write-only Sheets scope for
an arbitrary existing spreadsheet. The broader scope applies to the account's
spreadsheet files, not only to the configured tab. Use a dedicated account,
a dedicated spreadsheet, or protected ranges when a narrower operational
boundary is required. Studio records the scopes that Google actually granted.
Connector checks, runs, and deployments stop early if those scopes no longer
cover the project workflow.

\section{The running example}

The example is \path{zippergen/examples/tutorial_review.py}. It has three lifelines:

\begin{itemize}
  \item \textbf{Requester} initially owns a request and the maximum number of
        revision attempts, and receives the answer.
  \item \textbf{Writer} drafts a reply and revises it after rejection.
  \item \textbf{Reviewer} uses a separate LLM action to assess every draft,
        presents the draft and notes to a human authority, and owns the bounded
        retry loop.
\end{itemize}

The protocol is:

\begin{enumerate}
  \item Requester validates \texttt{max\_retries}, sends the request to Writer,
        and sends the retry budget to Reviewer.
  \item Writer uses an LLM action to create a draft.
  \item Writer sends the draft to Reviewer.
  \item Reviewer uses an LLM action to identify concerns, then presents both
        the draft and concerns in a human confirmation action.
  \item If Reviewer approves, the draft goes to Requester.
  \item If Reviewer rejects while revision attempts remain, Reviewer returns
        the draft to Writer; Writer revises it and presents the new draft to
        Reviewer again.
  \item If the retry budget is exhausted without approval, Requester receives
        an explicit failure notice instead of an unapproved draft.
\end{enumerate}

\section{Optional reference: one-process in-memory execution}

Studio's durable \texttt{run} is the recommended development command. This
short direct run is useful only for understanding the simpler in-memory
backend or debugging the Python module itself. Run the example directly:

\begin{lstlisting}[style=shell]
uv run --project zippergen python zippergen/examples/tutorial_review.py
\end{lstlisting}

Expected interaction:

\begin{lstlisting}[style=shell]
Draft:
[draft_reply:draft]

Automated reviewer notes:
[assess_draft:concerns]

Approve this draft? [y/n]: y
Result: [draft_reply:draft]
\end{lstlisting}

Run it again and enter \texttt{n}. Writer produces
\texttt{[revise\_reply:draft]}, Reviewer produces a new
\texttt{[assess\_draft:concerns]}, and the human is asked again; enter
\texttt{y} to accept that revision. If you keep entering \texttt{n}, the program stops after
two revision attempts and returns an explicit failure notice. This direct
program uses in-memory execution and an in-terminal human backend. It is
convenient for the first smoke test, but it does not demonstrate durable
restart behavior.

Internally, this memory backend runs entirely inside the one Python process
started by \texttt{uv run --project zippergen python}. It creates one Python thread for each
lifeline---Requester, Writer, and Reviewer in this example---and uses
thread-safe FIFO queues, keyed by sender, receiver, and channel, for their
messages. It does not create a separate operating-system process for each
lifeline. When the program exits or crashes, the threads, queues, messages, and
progress disappear together. The later SQLite backend still runs local
lifelines in threads, but records communication and execution progress in the
database so it can recover them after a restart.

\subsection{Task, task ID, and token}

The \emph{task} is the pending work itself: in this example, the rendered draft
and the request for a human decision. The \emph{task ID} is its stable internal
name. A trusted operator working locally can use that ID to select the task. A
\emph{token} is a separate, random bearer credential that an external adapter
can use instead of trusting a raw task ID. Protect a token like an approval
link. Both point to the same task; neither is the approval or rejection
decision.

From the project root:

\begin{lstlisting}[style=shell]
export ZIPPERGEN_HOME="$HOME/Projects/zippergen-tutorial/tutorial-runtime"
STORE="$ZIPPERGEN_HOME/runs/manual-review.sqlite"

zippergen run zippergen/examples/tutorial_review.py:tutorial_review \
  --llm mock \
  --input 'request=Explain why the sky is blue in two sentences.' \
  --input 'max_retries=2' \
  --store "$STORE" \
  --timeout 0
\end{lstlisting}

Each \texttt{--input} occurrence supplies one \texttt{name=value} pair. The
names match the parameters in
\texttt{tutorial\_review(request, max\_retries)}. ZipperGen parses
\texttt{max\_retries=2} as an integer. For many inputs, the two flags may be
replaced by one JSON object:

\begin{lstlisting}[style=shell]
--input-json '{"request":"Explain why the sky is blue.","max_retries":2}'
\end{lstlisting}

\texttt{STORE} is merely a short shell variable chosen by this tutorial, not a
special ZipperGen setting. The shell replaces \texttt{\$STORE} with the full
SQLite path before running each command. Terminal A prints that path and then
waits. Leave it running.
\texttt{--timeout 0} means no execution deadline; use this only when waiting is
intentional.

\subsection{Terminal B: inspect status and tasks}

Open a second terminal, enter the repository, and repeat both variable
assignments because a new terminal does not inherit them:

\begin{lstlisting}[style=shell]
cd "$HOME/Projects/zippergen-tutorial"
export ZIPPERGEN_HOME="$HOME/Projects/zippergen-tutorial/tutorial-runtime"
STORE="$ZIPPERGEN_HOME/runs/manual-review.sqlite"

zippergen status \
  --store "$STORE"

zippergen tasks \
  --store "$STORE"
\end{lstlisting}

Status should say \texttt{waiting}. The tasks command prints the rendered draft
and a task identifier. Copy the task identifier. Choose exactly one of the
following decisions; once the task is decided, do not run the other command for
the same task.

Approve it:

\begin{lstlisting}[style=shell]
zippergen approve \
  --store "$STORE" \
  --task <TASK-ID> --yes
\end{lstlisting}

Or, to exercise the rejection branch instead, reject it explicitly:

\begin{lstlisting}[style=shell]
zippergen approve \
  --store "$STORE" \
  --task <TASK-ID> --no
\end{lstlisting}

After rejection, Terminal A asks Writer for a revision and then waits on a
\emph{new} human task for the revised draft. List the pending tasks again, copy
the new task ID, and make the next decision:

\begin{lstlisting}[style=shell]
zippergen tasks --store "$STORE"

zippergen approve \
  --store "$STORE" \
  --task <NEW-TASK-ID> --yes
\end{lstlisting}

Every presented draft is a distinct task with its own task ID. Approving any
draft finishes successfully. Rejecting the initial draft and both permitted
revisions exhausts \texttt{max\_retries=2}; Terminal A then returns the explicit
failure notice and exits. Do not reuse an already-completed task ID.

The task ID is sufficient for this trusted local CLI exercise. External
adapters such as email, Telegram, or Slack can instead use durable tokens. To
display one, rerun the task listing as follows:

\begin{lstlisting}[style=shell]
zippergen tasks \
  --store "$STORE" \
  --tokens --channel cli
\end{lstlisting}

Here \texttt{cli} is only a descriptive token-namespace label; it is not a
workflow communication channel. Different adapter labels may have different
tokens for the same task. A token replaces the task ID, while \texttt{--yes} or
\texttt{--no} still determines the decision. For example, token-based rejection
is:

\begin{lstlisting}[style=shell]
zippergen approve \
  --store "$STORE" \
  --token <TOKEN> --no
\end{lstlisting}

After a draft is approved or the retry budget is exhausted, Terminal A prints
a JSON result and exits. Confirm completion and view the trace:

\begin{lstlisting}[style=shell]
zippergen status \
  --store "$STORE"

zippergen trace \
  --store "$STORE" --tail 30

zippergen tasks \
  --store "$STORE" --all
\end{lstlisting}

\begin{notebox}{Why rerunning may finish immediately}
The SQLite store records a completed result for this workflow. Running the same
workflow against the same store replays committed work instead of repeating it.
Point \texttt{STORE} at a new, explicitly named file for a genuinely new
tutorial run, for example
\texttt{STORE="\$ZIPPERGEN\_HOME/runs/manual-review-2.sqlite"}. Never delete a
production store merely to force a rerun.
\end{notebox}

cd "$HOME/Projects/zippergen-tutorial"

\section{Develop and refine with a coding assistant}

This section works on a copy so the canonical example remains available for
comparison and deployment.

\subsection{Create a branch and working copy}

\begin{lstlisting}[style=shell]
git switch -c tutorial/workflow-cycle
mkdir -p workbench
cp zippergen/examples/tutorial_review.py workbench/tutorial_review.py
git status --short
\end{lstlisting}

The \texttt{-c} form creates a new branch and therefore runs only once. If a
branch of that name already exists from your own earlier attempt, use
\texttt{git switch tutorial/workflow-cycle} instead. If
\path{workbench/tutorial_review.py} already exists, inspect it before deciding
whether to reuse it; do not overwrite work you do not understand.

Save a semantic baseline before any edit:

\begin{lstlisting}[style=shell]
export ZIPPERGEN_HOME="$HOME/Projects/zippergen-tutorial/tutorial-runtime"
mkdir -p "$ZIPPERGEN_HOME/snapshots"
SNAPSHOT="$ZIPPERGEN_HOME/snapshots/tutorial-before-$(date +%Y%m%d-%H%M%S).json"

  workbench/tutorial_review.py:tutorial_review \
  -o "$SNAPSHOT"
echo "$SNAPSHOT"
\end{lstlisting}

The timestamp makes the baseline unique, so rerunning the exercise cannot
silently replace the meaning you intended to preserve. Copy the absolute path
printed by \texttt{echo}; it is the value used below.

\subsection{Use a precise refinement prompt}

In Studio, import the workbench copy as the branch's project workflow and open
the scratch refinement. Studio shows the former and
incoming entries and asks for confirmation before changing the manifest:

\begin{lstlisting}[style=shell]
workflow import workbench/tutorial_review.py:tutorial_review
workflow edit-refinement
\end{lstlisting}

Paste the following text into the editor, save it, and exit:

\begin{lstlisting}[numbers=none]
# Add compliance review after exhaustion

If Reviewer exhausts the max_retries budget without approving a draft, a
separate Compliance human participant reviews the last draft. If Compliance
approves, release that draft to Requester; otherwise send the existing explicit
failure notice. Keep all Reviewer-approved paths and the retry bound unchanged.
\end{lstlisting}

Studio stores the text at \path{.zippergen/refinement.md}. Apply it, then
implement the revised canonical specification:

\begin{lstlisting}[style=shell]
workflow refine-spec
workflow status
workflow implement
\end{lstlisting}

The implementation task supplies the nested skill, canonical specification,
assistant-check contract, and explicit no-deployment boundary. Studio starts
Codex in the tutorial root with that fixed task.

\subsection{Independently verify the assistant's work}

Even if the assistant reports success, run these yourself. If this is a new
terminal, first restore \texttt{SNAPSHOT} using the absolute path printed
earlier:

\begin{lstlisting}[style=shell]
cd "$HOME/Projects/zippergen-tutorial"
SNAPSHOT='<ABSOLUTE-SEMANTIC-BASELINE-PATH>'
\end{lstlisting}

Replace the placeholder and keep the single quotes. Then run:

git status --short

\end{lstlisting}

The diff should show a Compliance lifeline, a new human action, new messages and
control structure on the retry-exhaustion path, and the deployment file-path
change. It should not show changes to Reviewer-approved paths or to the retry

renames, action implementation changes, participant ownership,
message/control context, execution order, parallel structure, and deployment

Run focused tests supplied by the assistant, then the full suite:

\end{lstlisting}

\subsection{Specification template for a workflow created from scratch}

Enter \texttt{workflow edit-spec} and use this structure in the automatically opened
\path{specification.md}:

\begin{lstlisting}[numbers=none]
# Workflow title

- Purpose and successful outcome: ...
- Participants and responsibilities: ...
- Inputs and initial owners: ...
- Messages and data crossing boundaries: ...
- LLM, deterministic, external-effect, and human actions: ...
- Decision and loop owners: ...
- Parallel work: ...
- Final outputs and owners: ...
- External services, credentials, and deployment constraints: ...
- Safety/idempotency requirements: ...
\end{lstlisting}

Later behavioral changes go into the scratch buffer opened by
\texttt{workflow edit-refinement}. \texttt{workflow refine-spec} integrates
the change into the canonical specification and consumes the buffer. Git,
rather than a pile of active prompt fragments, preserves history.

\section{Create a guided named deployment}

Return to the canonical example for a deterministic deployment exercise. Set
the tutorial runtime directory in the current terminal:

\begin{lstlisting}[style=shell]
export ZIPPERGEN_HOME="$HOME/Projects/zippergen-tutorial/tutorial-runtime"
\end{lstlisting}

Create the bundle, managed environment, profile, and service definitions, but
do not start a background service yet:

\begin{lstlisting}[style=shell]
zippergen deploy zippergen/examples/tutorial_review.py:tutorial_review \
  --name tutorial-review \
  --llm mock \
  --input 'request=Explain deployment in two simple sentences.' \
  --input 'max_retries=2' \
  --yes \
  --no-start
\end{lstlisting}

The default path performs these steps:

\begin{enumerate}
  \item load the source workflow and deployment declaration;
  \item collect defaults and command-line overrides;
  \item copy declared source files into a timestamped bundle;
  \item create a deployment-specific Python environment;
  \item install ZipperGen and declared packages;
  \item write the profile, run script, launchd plist, and systemd unit template;
  \item run doctor checks; and
  \item stop before service startup because of \texttt{--no-start}.
\end{enumerate}

\texttt{--yes} accepts declared defaults non-interactively. Omit it to see the
guided questions. It never means ``approve arbitrary live effects''; it only
controls configuration prompting.

\subsection{Inspect the generated artifacts}

\begin{lstlisting}[style=shell]
find "$ZIPPERGEN_HOME" -maxdepth 5 -type f -print | sort
zippergen doctor tutorial-review
\end{lstlisting}

Before the first run, doctor normally warns that the SQLite store and log do not
exist and that the service is not installed. Those warnings are expected;
failures are not.

\begin{longtable}{p{0.38\linewidth}p{0.55\linewidth}}
\toprule
\textbf{Path below \texttt{ZIPPERGEN\_HOME}} & \textbf{Purpose} \\
\midrule
\endhead
\path{deployments/tutorial-review.json} & Public deployment profile. \\
\path{deployments/tutorial-review.secrets.json} & Mode-0600 environment
secrets, created when required. It is empty for the mock tutorial. \\
\path{deployments/tutorial-review.sh} & Stable launch script. \\
\path{deployments/io.zippergen.tutorial-review.plist} & Generated macOS

\path{deployments/zippergen-tutorial-review.service} & Generated Linux systemd

\path{environments/tutorial-review/} & Managed Python environment. \\
\path{apps/tutorial-review/<timestamp>/} & Timestamped source bundle for this
deployment revision. \\
\path{runs/tutorial-review.sqlite} & Durable execution store. \\
\path{logs/tutorial-review.log} & Supervised-service standard output/error. \\
\bottomrule
\end{longtable}

Managed environments are disposable build products, unlike source history
and run stores. ZipperGen builds each replacement in a temporary sibling
directory, prefers \texttt{uv} so that no \texttt{ensurepip} bootstrap is
needed, installs dependencies there, and replaces the named environment only
after success. A failed build leaves the previous environment unchanged and
removes only its incomplete temporary directory.

\section{Optional: run as a supervised user service}

The example is finite, while supervised deployments are primarily intended for
long-running watchers and servers. To test supervision safely, use a second
deployment name and stop it immediately after completion.

\subsection{Prepare a fresh service deployment}

\begin{lstlisting}[style=shell]
export ZIPPERGEN_HOME="$HOME/Projects/zippergen-tutorial/tutorial-runtime"

zippergen deploy zippergen/examples/tutorial_review.py:tutorial_review \
  --name tutorial-review-service \
  --llm mock \
  --input 'request=Demonstrate durable restart in two sentences.' \
  --input 'max_retries=2' \
  --yes --no-start

zippergen start tutorial-review-service --dry-run
\end{lstlisting}

Read the dry-run commands. On macOS they use \texttt{launchctl}; on Linux they
use \texttt{systemctl --user}. If they look appropriate, start and enable the
service:

\begin{lstlisting}[style=shell]
zippergen start tutorial-review-service --enable
zippergen doctor tutorial-review-service
zippergen status tutorial-review-service
\end{lstlisting}

The status should become \texttt{waiting}. Test durability by restarting while
the human task is still pending:

\begin{lstlisting}[style=shell]
zippergen restart tutorial-review-service
zippergen status tutorial-review-service
\end{lstlisting}

The same task remains pending because it lives in SQLite, not only in process
memory.

Because this service was started with \texttt{--enable}, its generated launcher
records \path{ZIPPERGEN_HOME}. After a full reboot, the user service manager
normally starts it again when the user session starts: after graphical login on
macOS, or when the user systemd manager starts on Linux. No interactive shell
export is needed by the service itself. You still repeat the \texttt{cd} and
\texttt{export} commands before using ZipperGen CLI commands in a new terminal.

\subsection{Watch logs and approve}

In another terminal you may follow the log:

\begin{lstlisting}[style=shell]
export ZIPPERGEN_HOME="$HOME/Projects/zippergen-tutorial/tutorial-runtime"
zippergen logs tutorial-review-service --follow
\end{lstlisting}

Press Control-C to stop following the log; that does not stop the service.
List and approve the task:

\begin{lstlisting}[style=shell]
zippergen tasks \
  --store "$ZIPPERGEN_HOME/runs/tutorial-review-service.sqlite"

zippergen approve \
  --store "$ZIPPERGEN_HOME/runs/tutorial-review-service.sqlite" \
  --task <TASK-ID> --yes

zippergen status tutorial-review-service
zippergen stop tutorial-review-service
\end{lstlisting}

Stop promptly after the finite workflow completes. The generated supervisor is
configured to keep a deployment alive, which is correct for polling workflows
such as call intake but unnecessary for this finite tutorial.

If the machine does not support launchd or systemd user services, keep using:

\begin{lstlisting}[style=shell]
zippergen run-deployment tutorial-review-service
\end{lstlisting}

under your preferred terminal multiplexer or process supervisor.

\section{Update, reconfigure, and redeploy}

\subsection{Change persistent configuration}

For a long-running deployment, update declared fields and restart in one step:

\begin{lstlisting}[style=shell]
zippergen configure tutorial-review-service \
  --input 'request=A new configured request.' \
  --input 'max_retries=3' \
  --yes --restart
\end{lstlisting}

For this finite example, the existing store already contains a completed
result. Changing its input does not erase durable history or create a new job.
Use a new deployment name/store for a new finite execution. For a real watcher,
\texttt{configure --restart} is the normal pattern.

\subsection{Redeploy changed source}

After editing and validating the source, redeploy an existing named deployment:

\begin{lstlisting}[style=shell]
zippergen validate zippergen/examples/tutorial_review.py:tutorial_review
zippergen deploy tutorial-review-service --yes
\end{lstlisting}

This creates a new timestamped source bundle and starts the named deployment.
The stable SQLite store is retained, so already committed durable work is not
repeated.

To deploy the assistant-modified workbench version as a separate test:

\begin{lstlisting}[style=shell]
zippergen deploy workbench/tutorial_review.py:tutorial_review \
  --name tutorial-review-v2 \
  --llm mock \
  --input 'request=Test the compliance version.' \
  --input 'max_retries=2' \
  --yes --no-start
\end{lstlisting}

\subsection{Switch lifelines to real models only after mock success}

Replace \placeholder{OPENAI-MODEL} and \placeholder{ANTHROPIC-MODEL} with
identifiers available to your accounts. Keep the inherited default on mock and
override the two LLM-active lifelines. Omit \texttt{--yes} so the guided
command asks for both enabled secrets without putting either in shell history:

\begin{lstlisting}[style=shell]
zippergen configure tutorial-review-service \
  --llm mock \
  --llm-for 'Writer=openai:<OPENAI-MODEL>' \
  --llm-for 'Reviewer=claude:<ANTHROPIC-MODEL>' \
  --restart
\end{lstlisting}

The conditional OpenAI and Anthropic key fields now become active. ZipperGen
stores the values in the deployment's private mode-0600 secrets file, loads
them before importing the bundled workflow, and does not copy them into the
public profile or service definition. Use
\texttt{--llm-for Writer=inherit} to remove an existing override. If the
service is intentionally stopped, omit \texttt{--restart}; test later with
\texttt{run-deployment} or start it explicitly.

\begin{warningbox}{Never paste secrets into source or specifications}
Do not commit API keys, include them in a coding-assistant prompt, pass them via
\texttt{--set} on a shared shell history, or add them to a normal deployment
profile. Use the guided secret prompt or a securely managed environment.
\end{warningbox}

\section{Troubleshooting}

\subsection*{Managed environment creation aborts in \texttt{ensurepip}}

Older deployments created the environment directly with Python's
\texttt{venv.EnvBuilder(with\_pip=True)}. Some uv-managed Python builds can
abort inside the bundled \texttt{ensurepip} process, leaving a partially
created \path{environments/NAME} and a raw
\texttt{CalledProcessError}/\texttt{SIGABRT} traceback.

Update the editable ZipperGen installation, confirm \texttt{uv --version}, and
repeat the same Studio \texttt{deploy} command. Current ZipperGen creates a
fresh temporary environment with \texttt{uv}, installs into it, and atomically
replaces the old or partial directory only after success. Do not manually
delete the deployment profile, bundle, secrets, or run store. If creation
still fails, Studio reports whether failure occurred
during environment creation or dependency installation and confirms that the
previous environment was retained.

\subsection*{\texttt{uv: command not found}}

Restart the terminal after installing uv, then run \texttt{uv --version}. If it
still fails, follow the PATH instructions printed by the official installer.

\subsection*{\texttt{studio} is reported as an invalid top-level command}

The nested framework checkout or editable tool is older than this manual, or
the terminal is in another project. From the tutorial project root, inspect
before updating:

\begin{lstlisting}[style=shell]
pwd
git -C zippergen status --short
git -C zippergen branch --show-current
git -C zippergen remote -v
uv sync --project zippergen --python 3.12
uv tool install --force --editable ./zippergen
zippergen --help
\end{lstlisting}

If the worktree is clean and this is the intended remote/branch, use
\texttt{git -C zippergen pull --ff-only} and rerun the sync and editable tool
installation. ``Already up to date''
only means Git found no newer commit on the configured upstream; it does not
prove that the terminal is in the intended checkout or branch.

\subsection*{The shell reports \texttt{model} as an invalid command}

This is expected if you entered \texttt{zippergen model} in the
operating-system shell. \texttt{model} is a Studio command, not a top-level CLI
subcommand. Start Studio from the Git root, then enter it at the Studio prompt:

\begin{lstlisting}[style=shell]
zippergen
# The next line is entered only after zippergen [workflow]> appears:
model
\end{lstlisting}

If no project workflow is configured, enter \texttt{workflow list} and then
\texttt{workflow import PATH.py:NAME} using the displayed path.

\subsection*{Studio says the specification is empty}

Enter \texttt{workflow path} to see Studio's fixed path, then
\texttt{workflow edit-spec} to
open it again. Add at least one real requirement, save, and leave the editor.
The file must be valid nonempty UTF-8 text. No prompt directory, ID, or custom
filename is required. If importing an existing document with the advanced
\texttt{workflow edit-spec --file PATH} form, Studio reports the resolved absolute path
and distinguishes a missing file, directory, empty file, and invalid UTF-8.

\subsection*{The shell says \texttt{command not found: --input} or \texttt{--store}}

The preceding multiline command ended early. Re-enter the entire command and
ensure every continuation backslash is the final character on its line. This
same mistake can cause ZipperGen to report a missing workflow input because
only the first part of the intended command actually ran.

\subsection*{\texttt{model} lists no Writer or Reviewer}

Run \texttt{current} to confirm the project workflow, then
\texttt{workflow show actions}. Studio lists a lifeline in \texttt{model} only when that
lifeline contains an actual \texttt{@llm} action. A pure, human, or message-only
lifeline does not need a model. If the generated workflow was meant to contain
those actions, treat their absence as a generation/validation problem rather
than assigning a model to an unrelated participant.

\subsection*{A real model run reports an authentication or model error}

Use \texttt{model} to inspect configurations and assignments, then use
\texttt{model provider check NAME} for a fresh connection check and
\texttt{model config check NAME} for exact model availability.
Confirm that the account key belongs to that provider and that the named model
is enabled for the account. Do not print the key while diagnosing. To continue
the tutorial without network access or charges, enter
\texttt{model default mock}, restore participant inheritance with
\texttt{model inherit PARTICIPANT}, and start a fresh mock \texttt{run}.

\subsection*{The workflow file cannot be found}

Check the current directory and spec:

\begin{lstlisting}[style=shell]
pwd
ls zippergen/examples/tutorial_review.py
zippergen validate zippergen/examples/tutorial_review.py:tutorial_review
\end{lstlisting}

The text after the colon is the Python workflow object name, not the deployment
name.

\subsection*{Git asks for \texttt{user.name} or \texttt{user.email}}

Git cannot create the local commit until an author identity is configured.
Follow your organization or hosting provider's identity policy. To configure
only this tutorial checkout, run from its root:

\begin{lstlisting}[style=shell]
git config user.name "Your Name"
git config user.email "your-address@example.com"
git commit -m "Add reviewed answer workflow"
\end{lstlisting}

Replace both example values. Repository-local configuration avoids changing
other checkouts on the computer.

\subsection*{Validation or projection fails}

Do not deploy. Read the first failing check, inspect the global view and the
affected local projection, then ask the coding assistant to diagnose the error.
Common causes are missing messages, a decision owner that does not possess the
guard value, an output that is not present at the declared lifeline, or a
parallel data dependency.

\subsection*{No human task appears}

Confirm that Terminal A is still running and both commands use the same store:

\begin{lstlisting}[style=shell]
zippergen status --store /exact/path/to/store.sqlite
zippergen tasks --store /exact/path/to/store.sqlite --all
\end{lstlisting}

If status is \texttt{done}, that store already contains a result. Use a new
store path for a new finite run.

\subsection*{The service will not start}

\begin{lstlisting}[style=shell]
zippergen doctor tutorial-review-service
zippergen start tutorial-review-service --dry-run
zippergen logs tutorial-review-service --tail 100
\end{lstlisting}

On Linux, user systemd must be available. On macOS, \texttt{launchctl} must be
available in the logged-in graphical user session. Use
\texttt{run-deployment} as the foreground fallback.

\subsection*{Doctor shows warnings}

Before first execution, the deployment store should already be ready and
empty. A missing log or an uninstalled service before \texttt{start} is an
expected warning. A \texttt{FAIL} result blocks safe startup and should be
corrected.

\subsection*{A changed input does not create a new finite run}

Durable stores intentionally replay prior committed work. Use a new deployment
name or explicit new \texttt{--store} for a distinct finite job. Long-running
workflows normally retain their store across restarts and redeployments.

\subsection*{The semantic diff shows an unexpected change}

Use the full and local views to locate it. Do not dismiss unexpected lifeline,
ownership, message, action-kind, control, protocol-order, or deployment changes
as formatting. The semantic diff already ignores ordinary action formatting
and comments.

\section{Safe stopping, preservation, and cleanup}

Inside Studio, one named deployment is one operational unit. The preferred
cleanup path is:

\begin{lstlisting}[style=shell]
deploy stop tutorial-review-service
deploy remove tutorial-review-service
\end{lstlisting}

\texttt{deploy stop} only stops supervision. It preserves every deployment
artifact. \texttt{deploy remove} shows the exact ownership boundary, stops and
unregisters the service if needed, and archives the whole deployment under
\path{ZIPPERGEN_HOME/trash/deployments}. This includes its profile, private
deployment secrets, launch files, immutable bundle revisions, managed Python
environment, stable SQLite store and sidecars, and log.

The source checkout and project design remain. Named model configurations and
connector configurations also remain because other deployments may use them.
If another deployment refers to an allegedly owned path, Studio refuses
removal rather than moving shared state.

Use the permanent form only when recovery is not required:

\begin{lstlisting}[style=shell]
deploy remove tutorial-review-service --purge
\end{lstlisting}

The purge command requires the deployment name explicitly and asks you to type
the exact name before deletion. Scripts may add \texttt{--yes} only after
performing equivalent checks. There is deliberately no remove-all command.
The foreground deployment needs no stop command after it exits, but its named
profile and files still belong to the deployment and can be retired with the
same \texttt{deploy remove} command.

To reset only this project's private Studio/development context while retaining
the visible project, reopen Studio from the project root and enter:

\begin{lstlisting}[style=shell]
project reset state
\end{lstlisting}

The preview separates preserved project files from affected private state.
Answer \texttt{y} only after checking the project path and counts. On success,
Studio prints the exact backup directory below \path{ZIPPERGEN_HOME/resets} and
continues as \texttt{zippergen [no workflow]>}. Assistant requests, Studio
command history, run records, SQLite development stores, private development
keys, model/provider choices, and generated \path{.zippergen} task data are in
that backup rather than being deleted. The canonical specification, workflow
source, tests, manifest, Git
repository, and framework checkout remain where they were. Deployment
profiles, stores, logs, and running services are not part of this reset; retire
them separately with \texttt{deploy remove}. The explicit
\texttt{project reset state --yes} form is intended for scripts after
equivalent checks, not casual interactive use. To restart the design tutorial
instead, choose the fresh option from plain \texttt{project reset}; its preview
shows that the manifest, specification, and legacy prompt material will also
be archived while source, tests, and Git remain.

To abandon the workbench branch only after committing or otherwise preserving
anything important, switch back normally:

\begin{lstlisting}[style=shell]
git status --short
git switch main
\end{lstlisting}

Do not use destructive Git reset commands merely to clean up a tutorial.
